# 着手する Issue は人のラベルとマイルストーンと依存で選び、Issue ごとの worktree と上限の中で進める

## 背景と課題（Context and Problem Statement）

dev-autopilot は、Project に登録された Issue を AI が worktree で実装し、PR にして収束まで回す仕組みである（[要件メモ][memo] 1 節）。
進行役は AI ではなく Node のスクリプトで、「どの Issue を選ぶか」「待つか」「止めるか」を再現できる判定で行う（3 節）。
利用枠を消費する `claude -p` を無人で起動するため、選定を誤ると、着手してはいけない Issue に手を付けたり、
壊れた基線の上に積んだり、1 回の失敗で利用枠を使い切ったりする。

決めるのは次の 3 つである。

1. 進行役は、どの条件を満たす Issue を着手の候補にするか。候補が複数あるとき、どの順で、何件まで着手するか
2. 作業 AI の作業場所をどう分け、1 回のセッションに何の上限を掛け、上限に当たったときに何をするか
3. 間隔と上限をどこで変え、何を測って狭めるか

## 判断の決め手（Decision Drivers）

- 処理対象の判断は人が持つ（2 節「人の関所」）。AI が着手を自分で決めない
- 判定は決定的で再現できる（3 節）。同じ GitHub の状態なら同じ結果になる
- 判定できない状態では作業を増やさずに止める（6 節。fail-closed）
- 利用枠は有限で、1 回の実行・1 日・1 Issue のそれぞれに上限が要る（5 節 P8）
- 受け入れ率はリポでの実績とともに上がるので、少ない件数から始めて段階で広げる（11 節「失敗の教訓」）
- 将来は別リポジトリに分離するため、リポ固有の値はコードに書かず設定ファイル 1 つに出す（10 節）

## 検討した選択肢（Considered Options）

- 案 A：人が付けるラベル・マイルストーン・Issue 依存で範囲を決め、進行役が決定的に選ぶ
- 案 B：AI が Issue を読んで優先度を付け、着手する Issue を自分で選ぶ
- 案 C：マイルストーンの中の open な Issue をすべて順に処理する

## 決定（Decision Outcome）

採用した選択肢:「案 A：人が付けるラベル・マイルストーン・Issue 依存で範囲を決め、進行役が決定的に選ぶ」。
理由: 処理対象の判断を人に残したまま、判定を再現できる形にできる唯一の案だから。
業界の実践（OpenHands の `fix-me` ラベル、Linear の委任）とも同じ形になる。

### 着手の条件（4.1 節 R1-1〜R1-4）

進行役は Project の Issue を読み、次の条件をすべて満たすものだけを候補にする（R1-1）。1 つでも欠ければ候補にしない。

| 条件 | 見るもの |
| --- | --- |
| 人が処理対象にした | ラベル `agent-ready` がある |
| 版に属している | マイルストーンがある。候補が複数あれば、版の小さいマイルストーンを先にする |
| 未着手である | Project の Status が Todo |
| 依存が解けている | Issue 依存（blocked by）の相手がすべて閉じている |
| 人が止めていない | ラベル `needs-human` が無い。Project の単一選択欄「Agent」が `human` でない |
| 人が確かめた | `/verify-issue` の検証結果のコメント（コラボレータの投稿、印 `<!-- dev-autopilot: verified body=pass\|replace -->`）がある。`replace` なら本文を渡さず作業指示コメントだけを渡す |

`needs-human` と Agent 欄 `human` を除外する条件は、レビューの指摘「`needs-human` の Issue が翌日また選ばれる」を受けて足した（12 節「反映したもの」）。
人が外すまで再着手しない。往復の上限に当たった Issue は Status を Todo ではなく Blocked にし（R4-2）、Todo の条件でも弾かれるようにする。

候補のうち、進行中の Issue と触る範囲が重なりそうなものは、待たせずに着手し、重なりの予測を Issue に警告としてコメントする（R1-2、R5-3）。
待たせるのは人が入れた Issue 依存だけである（R5-2）。AI による競合の予測は補助に留め、判定に使わない。

1 回の実行で着手する件数に上限を持ち、最初は 1 件にする（R1-3）。1 日の着手は 3 件までにする（下記「費用の上限」）。
実行の記録（選んだ Issue、待たせた Issue と理由、使った時間）は、進行役の記録フォルダに実行ごとの JSON で残す（R1-4）。
記録フォルダは追跡しない。初期値は `dev-autopilot/records/` で、`.gitignore` に足す。

### 作業場所と上限（4.5 節 R5-1〜R5-4、4.2 節 R2-1・R2-2・R2-8・R2-11・R2-12・R2-13）

- Issue ごとに worktree を分け、同時に複数の Issue を進められるようにする（R5-1）。進行役は dev-autopilot 専用の clone を使い、
  `<repo>.worktrees/<ブランチ名>` に worktree を作って依存を入れ、worktree の中で `claude -p` を起動する（R2-1、12 節 判断 1）
- ブランチ名は `feat/issue-<番号>-<短い名前>` の形で、型（`feat` の部分）は Issue のラベルから決める（R2-2）。対応表は次のとおりで、設定ファイルに持つ

  | ラベル | 型 |
  | --- | --- |
  | `bug` | `fix` |
  | `enhancement` | `feat` |
  | `documentation` | `docs` |
  | それ以外 | `chore` |

- 着手の前に、worktree で品質ゲート（`pnpm check`）を 1 回回し、基線（`develop`）が緑であることを確かめる（R2-8）。
  赤なら Issue ごとに `needs-human` を付けるのではなく、実行全体を止めて運用 Issue に 1 回だけ知らせる。赤が直るまで着手しない。基線の赤は Issue の問題ではなく基盤の問題だからである
- テストを消す・skip する・期待値を緩める・lint を抑止する変更は、作業指示が明示していない限り禁止する。レビュー AI は違反を 🔴 として探す（R2-11）
- 1 回のセッションの上限を設定に持つ。初期値は 45 分・200 ターンに `--max-budget-usd` を加えたもの。ターンは `--max-turns` で止め、時間の上限は `claude` に無いので進行役が子プロセスを止める。
  上限に当たったら途中の状態を commit せず、worktree を残して `needs-human` を付ける（R2-12）
- 利用枠切れ（HTTP 429）・時間切れ・`claude` の異常終了は「実行の失敗」であり「作業の失敗」ではない。記録に別の欄で残し、`needs-human` を付けずに次回へ持ち越す。
  再試行は 3 回まで、間隔は 15 分。同じ失敗が 3 回続いたら `needs-human` を付ける（R2-13）
- `--output-format json` の `is_error` `num_turns` `usage` を記録に残し、1 Issue あたりの利用枠はそこから取る（R2-13）
- 先行の PR がマージされたら、依存していた worktree に `develop` を merge してから続ける（R5-4）。載せ直しに force push は使わない

### 費用の上限（5 節 P8、12 節「反映したもの」）

`claude -p` の実行は利用枠を消費するので、1 回の実行と 1 日あたりの上限を設定に持つ（P8）。
レビューの指摘「費用の上限が不足」を受け、1 Issue あたりの累計、サブエージェントの数、再試行の回数と間隔も設定に持つ（12 節「反映したもの」）。
初期値は次のとおり。

| 上限 | 初期値 |
| --- | --- |
| 1 回の実行で着手する Issue | 1 件 |
| 1 日に着手する Issue | 3 件 |
| 1 Issue の累計 | 12 セッションまたは 6 時間 |
| レビューの中のサブエージェント | 最大 4 体（3 軸＋批評者。ADR「レビューの Skill は change-review の核を残して v2 に組み直し、dev-autopilot に同封する」（[ADR-20261008-007][adr-20261008-007-review-skill-v2]）） |
| 再試行 | 3 回、間隔 15 分 |
| 1 日の利用枠 | `--max-budget-usd` の合計で設定する。初期値は未定で、メンテナが決める |

### 間隔の運用と指標（4.6 節 R6-1〜R6-3）

- 間隔と件数の上限は設定ファイル 1 つで変える。cron の設定と進行役の上限の両方を同じファイルから取る（R6-1）
- 間隔を狭める条件を先に決めておく。連続 N 回の実行で `needs-human` が 0 件、かつ利用枠の消費が上限内（R6-2）。N の初期値は 7（連続 7 回の実行で `needs-human` 0 件）
- 記録に残す指標：マージ率（着手した Issue のうちマージに届いた割合）、往復の回数、人が却下した指摘の割合（誤検知率）、マージ後の revert 率、1 Issue あたりの利用枠（R6-3）。
  revert 率は「マージした後に壊れていた」を測る唯一の値なので、進行役のマージの判定を信頼してよいかの判断に使う（revert の数え方は ADR「開発の PR のマージの可否は進行役が許可一覧の条件で判定し、マージの実行は人が行う」（[ADR-20261008-006][adr-20261008-006-orchestrator-merge-allowlist]））
- 指標は進行役の記録フォルダ（`dev-autopilot/records/`）の実行ごとの JSON から集計する。段階の出口（マージ率、往復の回数、却下率、revert 率、利用枠）の判定は、記録フォルダの集計だけを根拠にし、人の記憶や PR の目視では決めない

### 前提となる基盤（5 節 P1〜P5、9 節「業界の実践」、12 節 0b の結果）

着手の条件は、次の基盤が揃っていることを前提にする。基盤は `setup` が作り、`check` が毎回の最初に確かめる（4.9 節）。

| 基盤 | 内容 | 根拠 |
| --- | --- | --- |
| Project の Status | Todo / In Progress / Done に In Review・Ready to Merge・Blocked を足す。更新は GraphQL の `updateProjectV2ItemFieldValue`（Status は `singleSelectOptionId`） | P1、9 節「GitHub API」 |
| Project の単一選択欄「Agent」 | 値は `worker` `reviewer` `human` `paused`。Assignee は人のまま | P2、R2-6 |
| Issue 依存 | 処理対象にするときに人が入れる。読み書きは REST の `/repos/{owner}/{repo}/issues/{n}/dependencies/blocked_by` | P3、9 節「GitHub API」 |
| ラベル | `agent-ready`（処理対象）、`needs-human`（人が引き取る）、`from-review`（🟢 を起票した Issue） | P4、R4-1b |
| `develop` の ruleset | PR 必須・force push 禁止・base と最新であること。`required_approving_review_count` は 0、`require_extra_approval_for_unattributed_changes` は無効にする | P5、12 節 0b の結果 7 |

### 影響（Consequences）

- 良い点: 人が `agent-ready` を付けた Issue 以外に AI が手を付けない。着手の判断が GitHub の状態に残り、記録と突き合わせられる
- 良い点: 同じ GitHub の状態からは同じ選定になるので、段階 1（棚卸しだけ）で人が結果を検分できる
- 良い点: 実行の失敗と作業の失敗を分けるので、利用枠切れや一時的な障害で Issue が `needs-human` に落ちない
- 良い点: 上限がすべて設定ファイル 1 つにあるので、段階を進めるときにコードを触らずに広げられる
- 良い点: 段階の出口を記録フォルダの JSON から集計するので、判定の根拠が残り、後から検分できる
- 悪い点: 人の作業が増える。`/verify-issue` → 作業指示 → `agent-ready` → 依存の入力までを人がしないと、1 件も動かない
- 悪い点: 最初は 1 回 1 件なので、Issue が溜まっても処理は 1 日 1 件を超えない。段階 6 まで並列にならない
- 悪い点: 触る範囲の重なりは警告に留めるため、人が依存を入れ忘れると並行する PR が競合する。競合の解消は載せ直し（R5-4）と人に委ねる
- 悪い点: 基線（`develop`）が赤だと実行全体が止まり、赤が直るまで 1 件も着手しない。運用 Issue への通知を人が見落とすと、止まったまま日が過ぎる
- 中立: 条件が 1 つでも欠ければ候補にしないので、Project の欄やラベルの設定が崩れると黙って 0 件になる。`check` が基盤の存在を確かめることで補う

### 確認方法（Confirmation）

- 選定の判定（`select.ts`）は、偽の GitHub の応答を前提データにした単体テストで、条件ごとに「候補になる・ならない」を検査する
- 上限の判定（1 回の実行の件数・1 日の件数・ターン・時間・累計・再試行の回数と間隔）と「実行の失敗」の分類は、vitest で検査する
- ラベルから型への対応（`bug`→`fix`、`enhancement`→`feat`、`documentation`→`docs`、それ以外→`chore`）を vitest で検査する
- 基線が赤のとき、1 件も着手せず、運用 Issue への通知が 1 回の実行で 1 回だけであることを、結合テスト（偽の `gh` と赤の品質ゲート）で確かめる
- 実行ごとの JSON が記録フォルダに残り、指標の集計が JSON だけから再現できることを vitest で検査する
- 段階 1 の出口：7 回の実行で、選定・待機の結果に人が異議を出した回数 0（12 節「段階の割り直し」）
- `check` が、ラベル・Project の欄・ruleset・設定ファイルの項目と ID の実在を毎回の最初に確かめ、fail が 1 つでもあれば作業に入らない（S2）

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：人が付けるラベル・マイルストーン・Issue 依存で範囲を決め、進行役が決定的に選ぶ

- 良い点: 処理対象の判断が人に残る。Issue が外から立てられる公開リポでも、コラボレータが確かめた Issue だけが対象になる
- 良い点: 判定が決定的で、テストと記録で検分できる
- 良い点: OpenHands（`fix-me` ラベル）、Linear（人が Assignee のまま委任）、Jules・Copilot（セッションの上限）と同じ形で、業界の実践の中に収まる
- 中立: 選定の精度は人の運用（ラベル・依存の入力）に依存する
- 悪い点: 人の手順が増える。手順を文書に書き、`check` と `/verify-issue` で抜けを機械で止める必要がある

### 案 B：AI が Issue を読んで優先度を付け、着手する Issue を自分で選ぶ

- 良い点: 人がラベルや依存を入れなくても動く
- 悪い点: 選定が再現できない。同じ Issue 一覧でも実行のたびに結果が変わり、段階 1 で人が検分できない
- 悪い点: 外の人が書いた Issue の文を AI が読むことになり、4.8 節の「AI に渡すのはコラボレータの文だけ」に反する
- 悪い点: 選定にも利用枠を使う。処理対象を決めるだけで `claude -p` を起動することになる
- 悪い点: 「人が行き先を決め、AI が操縦する」という名前の由来（2 節）に反する

### 案 C：マイルストーンの中の open な Issue をすべて順に処理する

- 良い点: 仕組みが最も単純で、ラベルも Agent 欄も要らない
- 悪い点: ADR が要る Issue、曖昧な Issue、外の人の Issue にも手を付ける。Copilot の指針が「人に残す」とする曖昧な要件まで AI が触る
- 悪い点: `needs-human` に相当する止め方が無く、失敗した Issue を翌日また選ぶ
- 悪い点: 利用枠の消費を人が制御できない。Issue の数だけ実行する
- 悪い点: Issue 依存を見ないので、先行の Issue が終わる前に後続に着手し、競合する

## 補足情報（More Information）

- 着手の条件の前にある人の手順（`/verify-issue` → 作業指示コメント → `agent-ready`）と、渡す文の扱いは 4.8 節（I1〜I10）にある。本 ADR は進行役が読む条件だけを決める
- Status・Agent 欄・ラベルがどの順で変わるか（誰が、どの契機で）は要件メモ 4.10 節の遷移表にある。本 ADR は着手の条件（選定）だけを決める
- 実装の出力契約（R2-5）、計画のコメント（R2-9）、draft PR（R2-10）、レビューと対応ループ（4.3 節・4.4 節）、マージの条件（4.7 節。ADR-20261008-006）は別の ADR の対象とする
- 設定ファイルの項目（owner / repo、Project の番号と選択肢の ID、ラベル名、ラベルから型への対応、上限、記録フォルダの置き場）は 10 節の 2（ADR「dev-autopilot は分離を見越して 1 つのフォルダに Plugin の形で閉じ、導入と点検も Plugin が担う」（[ADR-20261008-008][adr-20261008-008-self-contained-plugin-layout]））に従い、dev-autopilot のコードには書かない
- 選定の実装は段階 1（棚卸しだけ）で動かし、段階 6 で並列と間隔の短縮に進む（7 節、12 節「段階の割り直し」）
- 本 ADR は [要件メモ][memo] の 4.1 節・4.2 節（R2-1・R2-2・R2-8・R2-11〜R2-13）・4.5 節・4.6 節・5 節（P1〜P5・P8）・11 節・12 節を元に起票した
