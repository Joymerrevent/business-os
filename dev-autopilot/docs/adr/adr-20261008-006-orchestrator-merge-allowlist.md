# 開発の PR のマージの可否は進行役が許可一覧の条件で判定し、マージの実行は人が行う

> **［2026-10-10 改め］** 起票時（2026-10-08）の題は「開発の PR は進行役が許可一覧の条件でマージし、方針に係る PR は人がマージする」で、段階 5 で進行役が `gh pr merge` を実行する決定だった。
> メンテナの判断で「判定は進行役、実行は人」に改め、実行を進行役に移すのは将来の別の ADR で決めることにした。proposed の間の書き直しなので、本文は改めた後の決定だけを書く。当初の案は「案 C」として残す。

## 背景と課題（Context and Problem Statement）

dev-autopilot は、人が処理対象にした Issue を作業 AI が実装して PR にし、レビュー AI の指摘が無くなるまで直すループである（[要件メモ][memo] 1 節）。
ループの終わりは「PR をマージする」操作であり、マージの可否を誰が判定し、誰が実行するかで、人に残る操作の数と、壊れたときの被害の範囲が決まる。

メンテナの個人設定（`~/.claude`）は「PR のマージは Claude が実行しない」と定め、リポの `.claude/settings.json` も `gh pr merge` を `permissions.ask` に置いている。
マージはレビュー完了の判断を伴い、本番デプロイを起動しうるからである。
2026-10-08 に調べた範囲（要件メモ 11 節）では、Copilot・Codex・Jules・Devin・OpenHands のどれも「PR を人が確認してマージ」で止まっており、
AI の判定で PR をマージする製品は見つからなかった。

課題を問いの形で書く。「どの PR を、誰が、どの条件で、どう確かめてマージしてよいと判定し、誰が実行するか」。
とくに、ADR・設計書・配布物の防衛（hook）・dev-autopilot 自身のような「方針に係る変更」が、人の目を通らずにマージされる経路を仕組みで塞げるか。
また、進行役の判定が信頼できるかを、実行を任せる前に測れるか。

## 判断の決め手（Decision Drivers）

- 人に残る操作を最小にすること。開発の PR で人に残るのは「印を見てマージを実行する」の 1 つだけにする
- マージの実行は人だけが行うこと（2026-10-10 の決定）。メンテナの個人設定と業界の実践（要件メモ 11 節）に揃え、AI の判定が外れたときの被害を「人が見てから」に限る
- 方針に係る変更（ADR・設計書・CLAUDE.md・配布物の防衛・dev-autopilot 自身）は判定の対象にせず、常に人の判断に渡すこと。自己改変の経路を残さない
- 判定が再現できること。進行役は AI ではなく Node のスクリプトで、判定は決定的な処理で行う（要件メモ 3 節）
- 壊れたときに安全側へ倒れること。判定できない状態では「マージしてよい」と言わず、人へ渡す（fail-closed）
- 判定の信頼度を測れること。人の判断と判定の一致を記録し、将来、実行を進行役に移すかを数で決められるようにする

## 検討した選択肢（Considered Options）

- 案 A：進行役が許可一覧の条件でマージの可否を判定して印として書き、マージの実行は人が行う（採用）
- 案 B：すべての PR を人が判定もマージもする（業界の標準）
- 案 C：段階 4 で信頼を積んだ後、進行役が許可一覧の条件で開発の PR をマージする（起票時の案。将来の選択肢として残す）
- 案 D：方針に係るパスの拒否一覧を持ち、拒否一覧に当たらない PR を進行役がマージする

## 決定（Decision Outcome）

採用した選択肢:「案 A：進行役が許可一覧の条件でマージの可否を判定して印として書き、マージの実行は人が行う」。
理由: 人に残る操作を 1 つにしつつ、マージの実行を人に残すという 2 つの決め手を同時に満たし、判定の信頼度を測れる唯一の選択肢だから。
案 C は業界の実践の外にあり、判定が信頼できると分かる前に実行まで任せることになる。案 B は判定の信頼度を測る機会が無い。案 D はレビューで自己改変の経路が見つかった。
案 C は捨てずに、段階 5 の出口を越えた後の将来の選択肢として残す（下の「実行を進行役に移す条件」）。

### 判定の主体と実行の主体（R7-1、R7-2b）

- マージの実行は人だけが行う。進行役は条件（下記）でマージの可否を判定し、結果を印として PR に書くまでを担う。AI のセッション（作業 AI・レビュー AI・批評者）には `gh pr merge` を許さず、進行役も `gh pr merge` を呼ばない（要件メモ 6 節。セッションの sandbox と鍵の分離は ADR「AI のセッションに sandbox を掛け、鍵は人用と自動化用に分け、作業 AI の commit は署名しない」（[ADR-20261008-004][adr-20261008-004-session-sandbox-and-keys]））。
- 判定の印は `merge=ready` か `merge=human` で、満たさない条件と head の SHA を添える。形は ADR「レビューの判定は PR コメントの印で行い head の SHA に結びつけ、🔴 🟡 だけを直して収束させる」（[ADR-20261008-005][adr-20261008-005-review-marker-and-convergence]）の印と同じ規則（進行役が投稿し、AI の出力には書かせない）に従い、正本は `dev-autopilot/src/marker.ts` の 1 定数に置く。
- `ready` なら PR を Ready to Merge にして人に渡す。`human` なら理由（満たさない条件）を添えて Ready to Merge のまま人に渡す。
- 人は印を見てマージする。印と違う判断をしたとき（`ready` をマージしない、`human` をマージする）は、その理由を PR にコメントする。この一致・不一致の記録が判定の信頼度になる（下の「続けるか止めるかの判断」）。
- 1 回の実行で `merge=ready` にするのは 1 件まで。人が 1 件マージするごとに、残りの PR は載せ直し（`git merge develop`。force push は使わない）と CI を経て判定し直す。
- `develop` の ruleset（`setup` が作る）に「base と最新であること」を入れ、古い base で pass した PR はマージされない。

### 進行役が「マージしてよい」と判定する条件（R7-2。すべて満たす）

1. dev-autopilot が作った PR で、向き先が `develop`。作者は人と同じアカウントなので作者では見分けられない。進行役の記録にある PR 番号であり、かつブランチ名が `feat/issue-<n>-*`（型は Issue のラベルから。対応表は ADR「着手する Issue は人のラベルとマイルストーンと依存で選び、Issue ごとの worktree と上限の中で進める」（[ADR-20261008-009][adr-20261008-009-issue-selection-worktrees-and-limits]））に一致するものに限る
2. 終了条件（ADR-20261008-005）を満たしている。最新のラウンドの印（進行役が付けたもの）が `verdict=pass`、印の `head` が PR の head と一致、CI 緑
3. push 前の漏えいの検査（R2-14）を通っている
4. 変更したファイルがすべて許可一覧（下記）にあり、diff の状態がすべて追加（A）か変更（M）
5. 変更したファイルに、方針に係るパス（下記の「含めない例」）が 1 つも無い

1 つでも満たさなければ `merge=human` とし、PR を Ready to Merge のまま人に渡す。判定できない状態（API の失敗、記録の欠け）も `merge=human` にする。

### 「マージしてよい」と判定してよいパスの許可一覧（R7-3）

拒否一覧ではなく許可一覧で持つ。一覧に無いパスを 1 つでも触れば `merge=human`。一覧は設定ファイル（要件メモ 10 節の正本 1 つ）に置く。

business-os の初期値は次の 3 つ（2026-10-08 決定、要件メモ 12 節の判断 2「狭く始める」）:

| パス | 中身 |
| --- | --- |
| `docs/usage/**` | 利用者向け文書 |
| `fixtures/**` | 検査の前提データ |
| `.changeset/*.md` | changeset。設定ファイル `config.json` は含まない |

`plugin/skills/**` と `plugin/scripts/**` は利用者の CC で動く配布物なので初期値に入れない。
`test/**` と `evals/**` も初期値に入れない。`evals/` には唯一の bash である `evals/scaffold.sh` と `evals/lib/**` の実行されるコードが、`test/**` には hook の fail-closed テストが含まれ、
テストの弱体化（消す・skip する・期待値を緩める）を許可一覧では止められず、レビュー頼みになるためである。
`test/**` `evals/**` `plugin/skills/**` `plugin/scripts/**` は、段階 5 で 10 件の一致を確かめた後、別の判断で広げる。

許可一覧に含めない（常に `merge=human`）例:

| 区分 | パス |
| --- | --- |
| 方針の正典 | `docs/adr/**` `docs/design/**` `ROADMAP.md` |
| CC の設定 | `CLAUDE.md` `.claude/**` |
| 自己改変 | `dev-autopilot/**` |
| Plugin の名札と CI | `.claude-plugin/**` `.github/**` |
| 利用者の CC で動く防衛と雛形 | `plugin/hooks/**` `plugin/agents/**` `plugin/templates/**` |
| 検査とその実装 | `test/**` `evals/**`、`plugin/scripts/check-repo.ts` など `check:*` の実装 |
| パッケージ・ロック・道具の設定 | `package.json` `pnpm-lock.yaml` `pnpm-workspace.yaml` `.node-version` `tsconfig.json` `vitest.config.ts` `eslint.config.*` `commitlint.config.*` `.gitleaks.toml` `.gitignore` `.markdownlint*` |
| ブランチ | `release/*` ブランチと `main` 向けの PR |

判定は diff の状態も見る。削除（D）・改名（R）・種類の変更（T。シンボリックリンク化など）・実行属性の変更は、パスが許可一覧にあっても `merge=human`。
実行属性の変更は `git diff --raw` の mode（変更前と変更後）の比較で検出する。`--name-status` には出ないので、`--name-status` だけで判定しない。

### 人がマージするときの手順（R7-3b）

- `gh pr merge --squash --match-head-commit <印の head SHA>` を使い、印の SHA と実際の head の一致をサーバ側でも強制する。手順は利用の文書に書く。将来、実行を進行役に移すときも同じコマンドにする。
- 印が `merge=human` の PR をマージするときは、満たさない条件を人が読んで判断し、理由を PR にコメントする。

### マージ後の後始末（R7-4）

進行役は次回の実行でマージされた PR を検出し、次を行う。

- Issue を閉じる（`develop` 向けの PR は `Closes #<番号>` で自動では閉じない）
- worktree を消す。ブランチはリポ設定 `delete_branch_on_merge` が消す
- 依存していた worktree に `develop` を merge する

### メンテナの個人設定との関係（R7-5）

マージの実行を人に残すので、メンテナの個人設定（`~/.claude`）の「PR のマージは Claude が実行しない」に例外は要らない。

- 進行役は `gh pr merge` を呼ばない。手動の `/dev-autopilot`（CC の中で進行役を動かす）でも同じで、リポの `.claude/settings.json` の `permissions.ask`（`gh pr merge`）はそのまま効く
- 判定（R7-2）の実装は vitest で検査する

### 実行を進行役に移す条件（R7-6。将来の選択肢）

段階 5 の出口（10 件で人の判断と進行役の判定が全件一致、revert 0 件）を満たしても、実行は自動では移さない。
移すなら本 ADR を改める新しい ADR で決め、そのときに次を揃える。

- 向き先が `develop`（`main` ではない）であること、方針に係るパスの除外、revert 率の監視、人の判断と判定の一致の確認（起票時に案 C の条件として挙げた 4 つ）
- メンテナの個人設定（`~/.claude`）の「PR のマージは Claude が実行しない」の例外の範囲と、`permissions.ask` との関係
- 実行を移した後に revert が 1 件でも出たら、人の実行に戻すこと

### 段階との関係（要件メモ 7 節・12 節「7 節の段階の割り直し」）

| 段階 | 判定 | 実行 | 出口 |
| --- | --- | --- | --- |
| 4 | 進行役は R7-2 の判定を記録に残すだけで印は書かない（shadow 判定） | 人 | 5 件のうち 4 件以上が往復 3 回以内で Ready to Merge。shadow 判定と人のマージの一致の件数を記録から測る |
| 5 | 進行役（R7-2 の条件）。印 `merge=ready` / `merge=human` を書く | 人 | 10 件で、人のマージの判断と進行役の判定が全件一致。revert 0 件。満たしても実行は人のまま |
| 6 | 進行役。並列と間隔の短縮 | 人 | R6-2 の条件 |
| 将来 | 進行役 | 進行役（別の ADR） | R7-6 の条件 |

### 続けるか止めるかの判断（R6-3）

進行役は指標を記録に残す。マージ率、往復の回数、人が却下した指摘の割合（誤検知率）、**マージ後の revert 率**、1 Issue あたりの利用枠、人の判断と判定の一致の件数。
revert 率は「マージした後に壊れていた」を測る唯一の値なので、判定を信頼してよいか（段階 5 の出口と、将来実行を移すか）の判断に使う。
revert は、`develop` の `revert:` で始まる commit（Conventional Commits の `revert` 型）のうち、本文でマージ commit の SHA を参照しているものを数える。
参考として、Codex 6.1%・Devin 14.5%・人 11.5% という調査がある（要件メモ R6-3）。

### 影響（Consequences）

- 良い点: 開発の PR で人に残る操作は「印を見てマージする」の 1 つになり、判定（条件の照合、許可一覧、diff の状態、印と head の一致）は人の記憶に頼らない
- 良い点: 方針に係る変更と自己改変は、許可一覧に無いという理由で仕組みが `merge=human` にする。人が見落としても、進行役が「よい」と言うことは無い
- 良い点: マージの実行が人なので、メンテナの個人設定の規則に例外ができず、業界の実践（人が確認してマージ）と同じ位置に立つ。判定が外れても被害は人の目の後にしか起きない
- 良い点: 印と人の判断の一致を数で測れるので、将来実行を移すかを根拠つきで決められる
- 良い点: `--match-head-commit` と ruleset の「base と最新」で、印と head のずれ・古い base の pass を GitHub 側でも止める
- 悪い点: 開発の PR のたびに人のマージの操作が 1 回残る。棚卸しの次の実行は、人がマージするまで依存する Issue に進めない
- 悪い点: 許可一覧が狭いので、`plugin/skills/**` `plugin/scripts/**` `test/**` `evals/**` を触る PR は当面すべて `merge=human` になる。印が `ready` になる範囲は利用者向け文書・前提データ・changeset に限られる
- 中立: 許可一覧を広げるとき、実行を進行役に移すときは、別の判断（新しい ADR か、ADR の改め）が要る

### 確認方法（Confirmation）

- R7-2 の判定（進行役の記録とブランチ名・向き先・印・CI・漏えい・パス・diff の状態）を進行役の 1 つの関数にし、vitest で次を検査する。
  許可一覧の外のパスを 1 つ含む PR、diff の状態が D/R/T の PR、`git diff --raw` の mode が変わった PR、`main` 向けの PR、印の head がずれた PR、CI が `pending` の PR、
  進行役の記録に PR 番号が無い PR、ブランチ名が `feat/issue-<n>-*` の形（型は Issue のラベルから）に合わない PR は、いずれも `merge=human` になる
- 結合テスト（偽の `gh`）で、進行役のどの経路からも `gh pr merge` が呼ばれないこと、1 回の実行で `merge=ready` の印を 2 件目に書かないことを確かめる
- 印の形（`merge=ready|human`、満たさない条件、head）が `dev-autopilot/src/marker.ts` の定数から作られ、AI の出力本文に同じ形の文字列があっても投稿前に取り除かれることを vitest で確かめる（ADR-20261008-005 と同じ規則）
- revert の検出（`revert:` で始まり、本文でマージ commit の SHA を参照する commit を数える）を vitest で検査する
- 段階 4 の shadow 判定が、記録に「マージしてよいか」の判定を残し、印を書かないことを結合テストで確かめる
- `check`（`/dev-autopilot check`）が、`develop` の ruleset に「PR 必須・force push 禁止・base と最新」があることを読み戻して確かめる
- 段階 5 の出口の 10 件は、人の判断と進行役の判定を Issue ごとに記録し、1 件でも食い違えば段階 4 に戻す
- 実行の記録に revert 率を残し、revert が 1 件でも出たら判定の条件を見直す

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：進行役が許可一覧の条件で判定し、実行は人が行う

要件メモ 4.7 節のとおり。許可一覧と diff の状態で判定の範囲を縛り、印を人に渡す。

- 良い点: マージの実行が人に残り、メンテナの個人設定と業界の実践に揃う。判定が外れても人の目の後にしか被害が出ない
- 良い点: 判定が決定的で、vitest で検査できる。人の判断との一致を数で測れる
- 良い点: 許可一覧は「書いたものだけ通す」ので、新しいフォルダが増えても既定で `merge=human` になる（安全側）
- 悪い点: 開発の PR のたびに人の操作が 1 回残る
- 中立: Copilot の「変更ファイルがすべて指定の glob に当たるときだけ approve を数える」と同じ考え方を、approve ではなく「マージしてよい」の印に当てている

### 案 B：すべての PR を人が判定もマージもする

Copilot・Codex・Jules・Devin・OpenHands と同じ形。進行役は PR を Ready to Merge にして止まる。

- 良い点: 業界の標準で、メンテナの個人設定の規則と矛盾しない
- 良い点: 判定の実装も許可一覧も要らない
- 悪い点: 条件の照合（印と head の一致、CI、パス、diff の状態）を人が毎回行う。見落としを仕組みで止められない
- 悪い点: 進行役の判定と人の判断の一致を測る機会が無く、将来実行を移す根拠が作れない

### 案 C：段階 4 で信頼を積んだ後、進行役が許可一覧の条件でマージを実行する

起票時（2026-10-08）の決定。段階 5 の出口（10 件の一致・revert 0 件）を越えてから、進行役が `gh pr merge --squash --match-head-commit` を実行する。

- 良い点: 開発の PR が人の操作なしで `develop` に入り、棚卸しから次の Issue へ進める。段階 6（並列と間隔の短縮）で人が律速にならない
- 悪い点: 業界の実践より踏み込んでいる。調べた製品で PR 自体をマージするものは無く、自動 approve まで行く CodeRabbit（条件つき）と Copilot（glob と設定で有効化）でもマージは人の操作が残る
- 悪い点: メンテナの個人設定（`~/.claude`）の規則に例外を作り、例外の範囲を cron が起動する進行役に限ると明記しても、読む人が混同しうる
- 悪い点: 判定が信頼できると分かる前に、実行まで任せる設計を先に固める
- 中立: 案 A で判定の信頼度を測った後なら、実行だけを移す変更で済む。将来の選択肢として R7-6 に残す

### 案 D：方針に係るパスの拒否一覧で判定する

方針に係るパス（ADR・設計書・CLAUDE.md など）を列挙し、拒否一覧に当たらない PR を通す。要件メモの初稿の形。

- 良い点: 一覧が短く、新しいフォルダを触る PR も通る
- 悪い点: 2026-10-08 のレビュー（要件メモ 12 節）で、拒否一覧に `dev-autopilot/**` が無く、自己改変の PR が通る経路が見つかった。列挙に漏れた瞬間に fail-open になる
- 悪い点: 削除・改名・種類の変更が判定の外にあった。パスだけ見ても、ファイルの消し方や置き換え方で防衛をすり抜ける
- 悪い点: フォルダが増えるたびに拒否一覧の更新を人が思い出す必要がある

レビューを受けて、許可一覧への反転と diff の状態の判定を R7-3 に反映した。

## 補足情報（More Information）

- 正本は [要件メモ][memo] の 4.7 節（R7-1〜R7-6）、4.6 節 R6-3、7 節と 12 節「7 節の段階の割り直し」、11 節「dev-autopilot が業界より先に出ている点」、12 節の判断 2
- 終了条件（CI 緑と `verdict=pass` の定義、印の形）は ADR-20261008-005 に書く。本 ADR は終了条件を満たした後のマージの判定だけを決める
- `develop` の ruleset・ラベル・設定ファイルを作る `setup` と、揃っているかを確かめる `check` は要件メモ 4.9 節
- 許可一覧に `test/**` `evals/**` `plugin/skills/**` `plugin/scripts/**` を足すかは、段階 5 の出口を越えた後に別の判断で決める。本 ADR の一覧を直接書き換えず、新しい ADR か改めの注記で扱う
- 指標（revert 率、人の判断と判定の一致の件数）は、進行役の記録フォルダの実行ごとの JSON から集計する。記録フォルダの置き場は ADR-20261008-009 に書く
- 分離（別リポジトリ化）の目安は段階 5 まで（要件メモ 10 節）。許可一覧の初期値は business-os 向けで、別のリポに適用するときは設定ファイルの値を差し替える
- 見直しの時期: 段階 5 の出口に達したとき（実行を移すかの判断。R7-6）、または revert が 1 件でも出たとき
