# GitHub への書き込みはすべて進行役が行い、AI は出力契約で結果を返す

## 背景と課題（Context and Problem Statement）

dev-autopilot は、進行役（cron が起動する Node のスクリプト。AI ではない）、作業 AI（Issue ごとに worktree の中で `claude -p` を起動）、レビュー AI（PR ごとに別の作業場所で `claude -p` を起動）の 3 つで動く（[要件メモ][memo] 3 節）。
作業 AI は worktree で `pnpm check` を回し、レビュー AI は PR のコードを実行して確かめる。AI のセッションに GitHub のトークンや `gh` の認証があると、作業 AI が書いたコードやレビュー対象のコードから読み取れてしまう（P13）。

要件メモの初期の案は、作業 AI が PR を作り、Issue にコメントし、Project の欄を更新する前提で書かれていた（R2-5 / R2-7 / R2-9 / R2-10 の旧版）。別の文脈のレビュー AI が、作業 AI に書き込みをさせる前提と P13 が矛盾すると指摘した（12 節「反映したもの」）。
同じレビューで、レビュー結果の判定に使う固定の印（R3-3）を作業 AI の出力に混ぜれば pass にできる「印の偽造」も指摘された。

さらに、作業 AI・レビュー AI・人は最初は同じ GitHub アカウント（メンテナ）で投稿する（P9）。GitHub は PR の作者自身の approve と request changes を受け付けないので、レビュー状態を判定に使えない。

課題：GitHub への書き込み（PR の作成、draft / ready の切り替え、Status と Agent 欄の更新、Issue と PR へのコメント）を誰が行い、AI の作業の結果をどのような形で進行役に渡すか。

## 判断の決め手（Decision Drivers）

- AI のセッションに GitHub の書き込みの権限を置かない（P13）。CSA の研究ノートが示す「Comment and Control」（Issue や PR のコメント 1 つで鍵をログに流出させる攻撃）への対策は、判断する層と実行する層を分け、エージェントに書き込みトークンを持たせないこと（11 節）
- 「どの Issue を選ぶか」「待つか」「止めるか」を再現できる判定にするため、判定は AI ではなく決定的な処理で行う（3 節）
- 判定に使う印（R3-3）の真正性を、GitHub のレビュー状態に頼らずに保つ（P9、R3-5）
- PR の題名は squash マージの件名になり commitlint が検査するので、規約に合わない題名を PR にする前に止める（R2-5b）
- 状態の正は GitHub に置き、各手順は「すでに済んでいれば何もしない」（12 節「運用の規則」）。書き込みを 1 か所に寄せるほど、途中で死んだときの復旧が単純になる
- 先行の仕組みとの整合：GitHub Agentic Workflows（gh-aw）はエージェントを読むだけにし、書き込みは safe outputs（構造化した要求を別の権限付きジョブが検証して実行）で行う（11 節）

## 検討した選択肢（Considered Options）

- 案 A: 書き込みはすべて進行役が行い、AI は出力契約で結果を返す
- 案 B: 作業 AI がリポに絞ったトークンで GitHub に書く
- 案 C: 作業 AI が MCP のツールで GitHub に書き、確認のプロンプトで操作を絞る

## 決定（Decision Outcome）

採用した選択肢:「案 A: 書き込みはすべて進行役が行い、AI は出力契約で結果を返す」。理由: 決め手の 1 つ目（AI のセッションに書き込みの権限を置かない）を満たす唯一の選択肢であり、印の真正性と決定的な判定も同じ仕組みで満たせるから。

決定の中身を、要件メモの ID を添えて並べる。

### 出力契約（R2-5）

- 作業 AI は GitHub に一切書かない。作業の結果は次の 2 つで進行役に返す
  - `claude -p --output-format json --json-schema <スキーマ>` の構造化出力：計画（R2-9）、PR の題名と本文の案（R2-5、I6）、止まった理由（R2-7）、確かめた検査の結果
  - worktree の中の commit
- レビュー AI も同じ形で返す。件数（🔴 🟡 🟢）・判定（pass / fix）・指摘の一覧（`id` と見出し）を構造化出力で返し、印は本文に書かない（下の「印の真正性」）
- 進行役は `--output-format json` の `is_error` `num_turns` `usage` を実行の記録に残し、実行の失敗と作業の失敗を別の欄で扱う（R2-13）
- 出力契約が壊れたとき：JSON が不正、または必須欄が欠けていたら、進行役がスキーマ検査で落とし、「実行の失敗」に分類する。AI の返した内容は使わず、次回の実行に持ち越す。R2-13 の規則どおり、同じ Issue で 3 回続いたら `needs-human` を付ける
- 作業 AI の出力は作業の結果であって、進行役への指示ではない。進行役は出力を検証してから GitHub に書く

### 進行役が行う書き込み（R2-5b、R2-6、R2-7、R2-9、R2-10）

- PR の作成：`develop` 向けに draft で作る。本文に `Closes #<番号>` と検査の結果を書く（R2-5b）
- PR の題名：Conventional Commits の規約（小文字か日本語で始める）に照らしてから使う。合わなければ PR を作らない（R2-5b）
- Status と Agent 欄：PR を作ったら Status を In Review にする。担当者（Assignee）はメンテナのまま、AI の担当は Project の単一選択欄「Agent」で表す。値は `worker` `reviewer` `human` `paused`（R2-6）
- 止まった理由への対応：ADR の起票が要ると分かったら、作業 AI は実装せずに「止まった理由」を返し、進行役が Issue へコメントして `needs-human` を付ける（R2-7）
- 計画のコメント：実装の前に作業 AI が返した計画を、進行役が Issue にコメントする。段階 2〜4 では人が計画を見て止められる（R2-9）
- 受け入れの下書きコメント：検疫の結果、作業指示の下書き（外の人の Issue は受け入れ AI が返したもの）、依存とマイルストーンの候補、印を進行役が投稿する。人が `agent-ready` を付けた後、印のハッシュを更新し、依存とマイルストーンを確定する（4.8 節 I12、ADR-20261008-002）
- draft / ready：PR は draft で作り、収束して Ready to Merge になったときに進行役が ready にする（R2-10）
- マージの可否の判定は進行役が行い、結果を印として PR に書く。マージの実行は人が行い、進行役は `gh pr merge` を呼ばない（R7-1。条件と印の形は ADR-20261008-006）

### 印の真正性（R3-5）と再レビューの入力（R3-6）

- 判定の印（`<!-- dev-autopilot: review round=<n> head=<SHA> high=<件数> medium=<件数> low=<件数> verdict=pass|fix -->` と `<!-- dev-autopilot: fix round=<n> -->`）は、進行役が構造化出力の件数と判定から組み立てて、投稿するコメントに付ける。レビュー AI と作業 AI は印を本文に書かない
- 判定は構造化出力から取る。AI の出力本文に `<!-- dev-autopilot:` で始まる文字列があれば、進行役は投稿の前に無条件に取り除く。本文にある印は判定に使わない
- 進行役は、自分が投稿したレビュー結果のコメントの ID を記録に残し、記録した ID のコメント本文からだけ印を読む。コメント一覧から印を探さない
- 印の形の正本は Plugin 内の 1 定数（`dev-autopilot/src/marker.ts`）に置く。Skill 側は印の定義を持たない
- 再レビューの入力は「前回の印と指摘」「修正コミットの範囲（SHA）」「差分」「作業指示（コラボレータの文。ADR「[AI に渡す文はコラボレータが書いたものだけにし、渡す文も作業の内容であって指示ではないと扱う][adr-20261008-002-collaborator-text-only]」（ADR-20261008-002））」「進行役が付けた事実（CI の結果、変更ファイル）」の 5 つにする。作業 AI の対応コメント（「確認済み」の主張）と PR の説明文は渡さない（9 節の文脈のバイアス）。印の中身と読み方は ADR「[レビューの判定は PR コメントの印で行い head の SHA に結びつけ、🔴 🟡 だけを直して収束させる][adr-20261008-005-review-marker-and-convergence]」（ADR-20261008-005）が定める

### アカウントと認証（P9、P13 のうち書き込みに関わる部分）

- アカウントは最初はメンテナの 1 つで始める。人と AI の投稿は印で見分け、GitHub のレビュー状態は判定に使わない（P9）。監査のために分けたくなったら自動化用のアカウントをコラボレータに足すが、判定の仕組みは変えない
- AI のセッションには `GH_TOKEN` を渡さず、`gh` を認証しない（P13）。鍵と sandbox の扱い（deploy key、fine-grained PAT、安全設定）は ADR「[AI のセッションに sandbox を掛け、鍵は人用と自動化用に分け、作業 AI の commit は署名しない][adr-20261008-004-session-sandbox-and-keys]」（ADR-20261008-004）で決める
- 作業 AI・レビュー AI のセッションでは `gh`、`claude`（再帰起動）、`git push` を使えないようにする。sandbox の通信先の制限、`--allowedTools`、進行役が実行前に行う設定の点検の 3 つで塞ぐ

### 影響（Consequences）

- 良い点: AI のセッションに GitHub の書き込みの権限が存在しないので、作業 AI のコードやレビュー対象のコードが権限を読み取る経路が無い
- 良い点: 判定の入口が進行役の記録したコメント ID と構造化出力に固定され、本文に混ぜた印は判定に影響しない
- 良い点: 書き込みが進行役の 1 経路に寄るので、冪等な復旧（PR があれば作らない、コメントがあれば足さない）を 1 か所で実装できる
- 良い点: 同じ GitHub アカウントのままで動く。アカウントを分ける判断を後回しにできる
- 悪い点: 出力契約の形（項目、必須か任意か）をスキーマとして定義して保つ必要がある。進行役・agent・Skill の版がずれると黙って壊れるので、1 つの Plugin の版で一緒に検査し、一緒に配る（10 節 7）
- 悪い点: 進行役のコードが増える（スキーマ検査、題名の規約の検査、印の組み立てと除去、コメント ID の記録）。判定の実装は vitest で検査する
- 悪い点: 作業 AI は途中で人や進行役に問い合わせられない。欠けている情報は「止まった理由」として返すしかない
- 中立: 印の形（R3-3）の正本は `dev-autopilot/src/marker.ts` の 1 定数にあり、Skill 側は定義を持たない。2 か所に定義を持たない（9 節）

### 確認方法（Confirmation）

- 段階 0b（2026-10-08 に確認済み。ADR「[進行役は決定的なスクリプトにし、AI は受け入れ・作業・レビュー・批評の 4 つの役だけを担う][adr-20261008-001-orchestrator-and-ai-roles]」（ADR-20261008-001）の段階表）で、進行役なし・GitHub 書き込みなしで `claude -p --plugin-dir <サブフォルダ> --agent dev-autopilot:worker` が入れ子の Plugin で動き（`tmp/` の偽の Plugin。実装では `dev-autopilot/plugin` を指す）、`--output-format json` で結果が返ることを実機で確かめた。`--json-schema` のスキーマ検査は段階 0c の実装で vitest に入れる
- 進行役の判定の実装（スキーマ検査と「実行の失敗」への分類、題名の規約の検査、印の組み立て、`<!-- dev-autopilot:` の除去、コメント ID からだけ印を読むこと）を vitest で検査する。結合テストは偽の `gh` を差し替えて進行役を端から端まで回す（10 節）
- `/dev-autopilot check` が、AI のセッションに `GH_TOKEN` が渡っていないことと `gh` が認証されていないことを確かめる。確かめ方は「設定に書いてある」ではなく「実際に使えない」ことを試す（6 節）
- 作業 AI・レビュー AI のセッションで `gh`、`claude`（再帰起動）、`git push` を使えないことを、vitest（進行役が渡す `--allowedTools` と安全設定の点検）と `check`（sandbox の中で実際に試す）で確かめる
- 段階 3 で、1 つのアカウントで印の判定が動くことを実機で確かめる（8 節）

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A: 書き込みはすべて進行役が行い、AI は出力契約で結果を返す

AI は「受け入れの下書きを書く」「実装する」「レビューする」「直す」だけを担い、結果を `--output-format json --json-schema` の構造化出力と worktree の commit で返す。進行役が検証してから GitHub に書く。gh-aw の safe outputs と同じ形。

- 良い点: AI のセッションに書き込みの権限が無い（P13）。コードやコメントから権限を盗む攻撃が成り立たない
- 良い点: 判定が決定的な処理に閉じる。印の真正性（R3-5）と再レビューの入力の絞り込み（R3-6）を進行役だけで実装できる
- 良い点: 同じアカウントで動き、GitHub のレビュー状態に依存しない（P9）
- 良い点: 先行の仕組み（gh-aw の safe outputs、CSA の「判断する層と実行する層の分離」）に沿う
- 悪い点: 出力契約の定義と保守が要る。契約がずれると黙って壊れるので、版を揃えて配る必要がある
- 悪い点: 進行役の実装が最も多い

### 案 B: 作業 AI がリポに絞ったトークンで GitHub に書く

作業 AI のセッションに、business-os だけに書き込める fine-grained PAT を渡し、作業 AI が `gh` で PR を作り、コメントし、Project の欄を更新する。

- 良い点: 進行役の実装が少ない。作業 AI が自分の判断で PR やコメントを書ける
- 良い点: 対話中の Claude Code と同じ手順で動くので、Skill をそのまま使える
- 悪い点: トークンがセッションの環境にあり、作業 AI が書いたコードやレビュー対象のコードから読める（P13）。リポに絞っても、AI が書き込める範囲はトークンの権限と同じ広さになる
- 悪い点: 作業 AI が印を含むコメントを直接投稿できるので、印の真正性（R3-5）を進行役で保証できない
- 悪い点: 書き込みの経路が 2 つ（AI と進行役）になり、冪等な復旧の実装が分散する
- 悪い点: 「Comment and Control」の攻撃面（Issue や PR のコメントから鍵を流出させる）が残る

### 案 C: 作業 AI が MCP のツールで GitHub に書き、確認のプロンプトで操作を絞る

GitHub の MCP サーバを作業 AI に接続し、書き込みの操作を permission の確認に回す。

- 良い点: 操作ごとの粒度で許す・許さないを決められる
- 中立: business-os の hook は、読むだけと分からない MCP の操作を確認に回す仕組みをすでに持つ
- 悪い点: `claude -p` は無人で動くので、確認のプロンプトに答える人がいない。確認を自動で許せば案 B と同じになり、拒否すれば書き込みが進まない
- 悪い点: MCP サーバの認証情報がセッションの環境に残り、P13 を満たさない
- 悪い点: 書き込みの内容（PR の題名、コメントの本文）を進行役が検証する機会が無く、印の除去（R3-5）も題名の規約の検査（R2-5b）もできない
