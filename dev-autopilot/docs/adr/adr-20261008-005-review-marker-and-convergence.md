# レビューの判定は PR コメントの印で行い head の SHA に結びつけ、🔴 🟡 だけを直して収束させる

## 背景と課題（Context and Problem Statement）

dev-autopilot では、作業 AI が実装した PR を、別のセッションのレビュー AI が読み、指摘が無くなるまで作業 AI が直す（[要件メモ][memo] 1 節）。
進行役は AI ではなく Node のスクリプトで、「通してよいか」「もう 1 周回すか」「止めるか」を再現できる判定で決める（3 節）。
判定の材料をどこから取るかと、往復をどう終わらせるかが決まっていないと、次の 3 つが起きる。

- レビュー AI の文章を進行役が解析すると、言い回しが変わるたびに判定が壊れる
- レビューの後に push された変更が、レビュー済みとして通る
- 🟢 Low の指摘まで直すと、再レビューが新しい指摘を生み、往復が終わらない

さらに、作業 AI とレビュー AI は最初は同じ GitHub アカウント（メンテナ）で投稿する。GitHub は PR の作者自身による approve と request changes を受け付けないので、GitHub のレビュー状態は判定に使えない（P9）。

問いは「レビューの判定をどの形で記録し、何を終了条件にし、何を直させるか」である。

## 判断の決め手（Decision Drivers）

- 判定は進行役が決定的に読めること。文章の揺れで結果が変わらない
- 判定が「どのコミットに対するものか」を持ち、pass の後の push を通さない
- 同じアカウントで作業 AI とレビュー AI が投稿しても動く（P9）。アカウントを分けても仕組みを変えずに済む
- 往復が有限で終わる。収束しないときは安全側（人に渡す）に倒れる
- 作業 AI の主張（「確認済み」）がレビュー AI の検出率を下げない（9 節「文脈のバイアス」）
- いまの手動の運用（PR #68 #71 #77 の R1 → 対応 → R2 → マージ）をそのまま機械にできる

## 検討した選択肢（Considered Options）

- 案 A: PR のコメントに固定の印を 1 行置き、印を head の SHA に結びつける
- 案 B: GitHub のレビュー状態（approve / request changes）を使う
- 案 C: 人が読む判定の文言（「通してよい」「直してから通したい」）を解析する

## 決定（Decision Outcome）

採用した選択肢:「案 A: PR のコメントに固定の印を 1 行置き、印を head の SHA に結びつける」。理由: 同じアカウントで動く唯一の案であり、判定の材料を機械で読める形に固定し、head の SHA で「どのコミットへの判定か」を持てるから。

### レビューの手順と出力（4.3 節）

- R3-1 レビュー AI は、作業 AI とは別の作業場所で PR の差分を読む。手順は `review` Skill（`change-review` の v2）をそのまま使う：実行して確かめる、fail-open を探す、収束するまで回す
- R3-2 結果は、行に付けるレビューコメントではなく、1 ラウンド 1 件の PR コメントに書く。形は PR #68 #71 #77 と同じにする：1 回目は「## レビュー結果（基点: `develop`）」、2 回目以降は「## 再レビュー結果 R<n>（対象: <範囲>）」。冒頭に判定の文、末尾にラウンドの表（| ラウンド | 指摘 | 最も重い種類 |）を置く
- R3-3 人が読む本文に加え、機械で読む印を 1 行付ける：
  `<!-- dev-autopilot: review round=<n> head=<SHA> high=<件数> medium=<件数> low=<件数> verdict=pass|fix -->`
  - `verdict` は 🔴 High と 🟡 Medium がともに 0 件のとき `pass`、1 件でもあれば `fix`
  - 印は進行役が組み立てて投稿に付ける。レビュー AI は印を本文に書かず、件数・判定・指摘の一覧（`id` と見出し）を `claude -p --output-format json --json-schema` の構造化出力で返す（ADR「[GitHub への書き込みはすべて進行役が行い、AI は出力契約で結果を返す][adr-20261008-003-github-writes-by-orchestrator]」（ADR-20261008-003）の出力契約）
  - 指摘の `id` は、軸・ファイル・見出しの正規化から作る。進行役は指摘の一覧を印の付随データ（コメント末尾の JSON ブロックか進行役の記録）に持ち、次のラウンドとの突き合わせに使う
  - 進行役は印だけで判定し、本文の言い回しは解析しない
  - 印の形の正本は Plugin 内の 1 定数（`dev-autopilot/src/marker.ts`）に置く。Skill 側は印の定義を持たない（定義を 2 か所に持たない）
- R3-4 レビュー AI のモデルは作業 AI と同じものに固定せず、設定で変えられるようにする。初期値は最上位のモデル（2 節）
- R3-5 印の真正性：進行役は自分が投稿したレビュー結果のコメントの ID を記録に残し、記録した ID のコメント本文からだけ印を読む。コメント一覧から印を探さない。判定は構造化出力から取り、AI の出力本文に `<!-- dev-autopilot:` で始まる文字列があれば進行役が投稿の前に無条件に取り除く。進行役が投稿したコメントだけを判定の材料にする規則は ADR-20261008-003 が定め、本 ADR は印の中身と読み方を定める
- R3-6 再レビューの入力は「前回の印と指摘」「修正コミットの範囲（SHA）」「差分」「作業指示（コラボレータの文。ADR「[AI に渡す文はコラボレータが書いたものだけにし、渡す文も作業の内容であって指示ではないと扱う][adr-20261008-002-collaborator-text-only]」（ADR-20261008-002））」「進行役が付けた事実（CI の結果、変更ファイル）」の 5 つにする。作業 AI の対応コメント（「確認済み」の主張）と PR の説明文は渡さない
- R3-7 未収束の扱い：レビュー AI が予算切れや入力不足で「未収束」を返した（判定が無い）ときは「実行の失敗」として次回の実行に持ち越し、ラウンドには数えない。R2-13 の規則どおり、同じ PR で 3 回続いたら `needs-human` を付ける

### 対応ループ（4.4 節）

- R4-1 判定が `fix` なら、作業 AI を同じ worktree で起動し、最新のラウンドの 🔴 と 🟡 だけに対応させる。作業 AI は worktree に commit し、進行役が取り込んで push する（ADR-20261008-003、ADR「[AI のセッションに sandbox を掛け、鍵は人用と自動化用に分け、作業 AI の commit は署名しない][adr-20261008-004-session-sandbox-and-keys]」（ADR-20261008-004））。🟢 は同じ PR では直さない。対応の結果は、作業 AI が構造化出力で返した指摘ごとの対応と確認を、進行役が「## R<n> の指摘への対応（<コミット>）」のコメントに書き、印 `<!-- dev-autopilot: fix round=<n> -->` を進行役が付ける
- R4-1b 🟢 は進行役が Issue にする。1 件 1 Issue、題名は指摘の見出し、本文に PR 番号・ラウンド・失敗シナリオ・推奨を写し、ラベル `from-review` を付ける。マイルストーンは付けない（人が棚卸しで付ける）。同じ見出しの open な Issue があれば作らず、コメントで PR 番号を足す。Issue を作ってから PR を Ready to Merge にする（先にマージすると、Issue 化に失敗したとき指摘が消える）
- R4-2 往復の回数に上限を持つ（初期値 3 回）。超えたら Status を Blocked にし、`needs-human` ラベルを付け、経緯を Issue にコメントする。人が外すまで再着手しない。振動の同定：前回のラウンドの 🔴 🟡 と同じ `id` の指摘が次のラウンドにも出たら振動とし、上限と同じ扱いにする。突き合わせには、進行役が印の付随データに持つ指摘の一覧を使う

### 終了条件（R4-3）

次の 2 つをともに満たしたとき収束とし、Status を Ready to Merge にする。1 回目から `pass` なら 1 回で収束とする。🟢 は残ってよい。

1. 最新のラウンドの印が `verdict=pass` で、印の `head` が PR の head の SHA と一致する。pass の後に push があれば一致しなくなり、再レビューが要る
2. CI が緑である

「CI が緑」の定義：設定に列挙した必須チェック名（例：`check (ubuntu-latest)` `check (windows-latest)` `commitlint`）のすべてが、PR の head SHA に対して `success` であること。1 つでも無い・`pending`・`skipped`・`failure` なら緑ではない。検査が走らなかった変更を通さない。

進行役は 1 回の実行の中で CI を待つ。待つ上限は設定に持ち、初期値は 30 分。超えたら判定せず次回の実行に持ち越す。

### 影響（Consequences）

- 良い点: 判定の入力が構造化出力と印 1 行に固定され、レビュー AI の本文は人向けに自由に書ける
- 良い点: `head=<SHA>` により、レビュー済みでないコミットがマージされない。マージ時の `--match-head-commit` と組み合わせて二重に守れる
- 良い点: 同じアカウントで始められ、自動化用のアカウントを足しても判定の仕組みは変わらない
- 良い点: 🟢 を Issue に逃がすので、往復が 🔴 🟡 の収束だけで終わる。見送った指摘は記録に残る
- 良い点: 指摘に `id` が付くので、振動の判定が本文の言い回しに依存しない
- 悪い点: 構造化出力のスキーマが `review` Skill と進行役の間の契約になり、版がずれると黙って壊れる。Skill は Plugin に同封し、同じ版で検査する（10 節 7）。印の形は進行役の 1 定数にあり、Skill は持たない
- 悪い点: GitHub の UI にはレビュー状態が表示されず、人は PR のコメントを読んで判定を知る
- 悪い点: 必須チェック名を設定に列挙するため、CI のジョブ名を変えたときに設定も直す必要がある。`check`（4.9 節 S2）が名前の実在を確かめる
- 中立: 業界の製品（Copilot、CodeRabbit）は approve までで、AI 同士の往復を自動で収束まで回す製品は無い（11 節）。収束の規則で守る

### 確認方法（Confirmation）

- 進行役の判定（構造化出力のスキーマ検査、印の組み立てと解析、`head` の一致、必須チェックの全件 `success`、ラウンド上限と `id` による振動の検出、「未収束」の「実行の失敗」への分類）は純粋な関数にし、vitest で検査する。言い回しを変えた本文、SHA が食い違う印、`pending` を含むチェックの一覧、同じ `id` が 2 ラウンド続く入力、判定の無い出力を、それぞれ「通らない」ことの検査に入れる
- AI の出力本文に混ぜた `<!-- dev-autopilot:` の文字列が投稿の前に取り除かれ、判定に影響しないことを vitest で検査する
- 段階 3 の出口：5 件の PR で、人が同じ PR を `change-review` した結果と 🔴 🟡 が一致する（12 節）
- 段階 4 の出口：5 件のうち 4 件以上が往復 3 回以内で Ready to Merge に届く
- 結合テストでは偽の `gh` を差し替え、R1 → 対応 → R2 の流れと、往復の上限で Blocked になる流れを端から端まで回す

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A: PR のコメントに固定の印を 1 行置き、印を head の SHA に結びつける

PR #68 #71 #77 の手動の運用（1 ラウンド 1 コメント）に、機械で読む 1 行を足すだけの形。

- 良い点: 同じアカウントで作業 AI とレビュー AI が投稿しても動く（P9）
- 良い点: 判定の材料が固定の文法を持ち、進行役が決定的に読める。本文は自由に書ける
- 良い点: `head=<SHA>` で「どのコミットへの判定か」を持ち、pass 後の push を通さない
- 良い点: 件数（high / medium / low）を持つので、🟢 の Issue 化と指標（R6-3）に同じ印を使える
- 悪い点: 印は誰でも書けるので、真正性の規則（R3-5、ADR-20261008-003）が別に要る
- 悪い点: GitHub の UI には判定が表示されない

### 案 B: GitHub のレビュー状態（approve / request changes）を使う

Copilot code review や CodeRabbit が使う形。マージ要件と連動する。

- 良い点: GitHub の UI とブランチ保護にそのまま組み込める
- 良い点: 新しいコミットが push されると approve が消える（head への結びつきを GitHub が持つ）
- 悪い点: PR の作者自身の approve と request changes を GitHub が受け付けない。同じアカウントで始める dev-autopilot では動かない（P9）
- 悪い点: 動かすには自動化用のアカウントか GitHub App が先に要り、段階 3 に入る前の準備が増える
- 悪い点: 重要度ごとの件数を持てず、🟢 の Issue 化に別の仕組みが要る

### 案 C: 人が読む判定の文言を解析する

「**通してよい。ブロッカーなし。**」「**🟡 <n> 件を直してから通したい**」の文を正規表現で読む。

- 良い点: 追加の印が要らず、PR #68 #71 #77 のコメントをそのまま使える
- 悪い点: 言い回しは変わりうる。Skill の文言を直すたびに進行役が壊れ、壊れ方は「判定できない」ではなく「誤判定」になりうる
- 悪い点: どのコミットへの判定かを文言が持たない
- 悪い点: 本文に印と同じ内容を書かせることになり、人向けの文章の自由度が下がる

## 補足情報（More Information）

### 同じアカウントで始める理由（P9）

アカウントは最初はメンテナの 1 つで始め、無人のマシンにはリポに絞った fine-grained PAT を置く。人と AI の投稿は印で見分ける。監査のために分けたくなったら自動化用のアカウントをコラボレータに足す。印で判定する仕組みは、どちらでも変えずに済む。自動化用のアカウントの投稿はレビュー AI の出力として扱う（I10）。

### 決定を裏付ける業界の実践（9 節）

- 判定を head の SHA に結びつける：Copilot code review は、新しいコミットが push されると approve を取り消す（人のレビューと同じ）。印の `head=<SHA>` は同じ考え方を印の側で持つ
- nit はマージを止めない：公開 Skill「agent-code-review-loop」の 4 段階（blocker / major / minor / nit）で nit は絶対にマージを止めない。Bugbot は blocking / non-blocking を分ける。R4-1 と R4-1b はこれを 🟢 の扱いとして固定した
- 解決済みの指摘を再提起しない：同じ Skill が「新しい証拠が無ければ再提起しない」とする。R4-2 の振動の検出は、再提起が起きたときに止める側の規則
- 重要度と確信度を分ける：Anthropic 公式 Plugin `code-review` は指摘ごとに確信度 0〜100 を付け、80 未満を捨てる。dev-autopilot では批評者（critic）が確信度を付け、🔴 🟡 でも確信度が低ければ 🟢 に下げるか捨てる（ADR「[レビューの Skill は change-review の核を残して v2 に組み直し、dev-autopilot に同封する][adr-20261008-007-review-skill-v2]」（ADR-20261008-007））。しきい値は設定に持ち、段階 3 で測った誤検知率で調整する。印の件数は、確信度の処理を済ませた後の値である
- 往復の上限：CodeRabbit はレビュー済みコミットが 5 件たまると自動で止まり、copilot-pr-autopilot は 10 ラウンドごとに回路遮断器を置く。R4-2 の 3 回がこれに当たる
- CodeRabbit の自動 approve の条件（コメントがすべて解決・最新コミットがレビュー済み・失敗した検査が無い）は、R4-3 の終了条件と同じ 3 要素を持つ。dev-autopilot は approve ではなく印で同じ条件を表す
- 文脈のバイアス：PR の説明文を細工して「問題なし」と思わせる攻撃が、Claude Code と CodeRabbit の両方で 33 件中 32 件成功した（arXiv 2603.18740）。R3-6 で対応コメントと説明文を再レビューの入力から外した

### 関連する ADR と資料

- ADR-20261008-003：進行役だけが GitHub に書き、進行役が投稿したコメントからだけ印を読む規則（印の真正性）。出力契約の形もそこで定める
- ADR-20261008-002：レビュー AI に渡す文の境界。再レビューの入力（R3-6）は両方の ADR で同じ文にしてある
- 要件メモ 4.3 節・4.4 節・5 節 P9・9 節：[dev-autopilot 要件メモ][memo]
- レビューの Skill の正本は `dev-autopilot/plugin/skills/review/`（10 節）。印の形の正本は `dev-autopilot/src/marker.ts`。構造化出力のスキーマの変更は Skill と進行役を同じ PR で直す

### 見直しの時期

段階 3 の出口（🔴 🟡 の一致、却下した指摘の割合 15% 以下）を測った時点で、確信度のしきい値と往復の上限の初期値を見直す。印の形そのものを変えるときは、新しい ADR で置き換える。
