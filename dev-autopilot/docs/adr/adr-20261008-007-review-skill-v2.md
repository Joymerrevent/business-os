# レビューの Skill は change-review の核を残して v2 に組み直し、dev-autopilot に同封する

## 背景と課題（Context and Problem Statement）

dev-autopilot のレビュー AI は、作業 AI とは別の作業場所で PR の差分を読み、収束するまでレビューを回す（[要件メモ][memo] R3-1）。
レビューの手順にはメンテナの個人設定（`~/.claude`）にある `change-review` Skill（SKILL.md 146 行、参照 5 ファイル、bash 1 本）を使う予定だったが、
メンテナの個人設定（`~/.claude`）は dev-autopilot の専用マシンには無いかもしれない（P14）。

2026-10-07 に `change-review` を評価した結果（9 節）、核は dev-autopilot に使える。

- 読む前に「実行して確かめる」を払う手順で、PR #68 #71 #77 では 1 回目で重い指摘が出て 2 回目で収束した
- 壊れ方の表（breakage-matrix）を機械的に当てるので、レビュー AI の気分で指摘の網が変わりにくい。fail-open を最重視する点は business-os の設計哲学と同じ
- 指摘ごとに重要度（🔴 🟡 🟢）・失敗シナリオ・証拠レベルを必ず書かせる。重要度の定義が印（R3-3。ADR「レビューの判定は PR コメントの印で行い head の SHA に結びつけ、🔴 🟡 だけを直して収束させる」（[ADR-20261008-005][adr-20261008-005-review-marker-and-convergence]））の判定にそのまま使える
- 止めどきの規則（🟢 だけになったら直さずに記録して終わる）と「見送った 🟢 は Issue に起票する」が、すでに Skill に書いてある。R4-1b は Skill の規則を機械にしたもの
- 「収束していないなら未収束と書く」を求めるので、時間切れでも「通してよい」を偽らない
- 診断だけで修正しないので、作業 AI と役割が混ざらない

一方で、無人で使うには足りない点が 6 つある（S1〜S6）。人に聞く箇所が 2 か所ある、再レビューの入り口が無い、機械で読める出力が無い、
予算の概念が無い、修正する側とレビューする側が同じ人である前提、`per-commit-gates.sh` が bash（business-os は bash を足さない規則）。
組み込みの `/code-review` と mattpocock の `code-review` と比べても、仕様の軸・指摘ごとの再検証・固定の出力・無人の入り口の 4 つが欠けている。

問い：dev-autopilot のレビューの Skill を、どう用意し、どこに置くか。

## 判断の決め手（Decision Drivers）

- 無人で動くこと。人に聞かず、予算（ターン・時間）の中で、機械が読める判定を返す（S1・S3・S4）
- 収束の設計を失わないこと。🟢 で止める規則・🟢 の Issue 化・振動の検出は、比べた 3 つの Skill の中で `change-review` だけが持つ
- 誤検知を抑えること。業界の誤検知率 5〜15% を目標にし、指摘ごとの再検証と確信度で落とす
- 信頼の境界を守ること。作業 AI の主張（PR の説明文）を読ませると検出率が下がる（文脈のバイアス）
- 進行役・agent・Skill の版がずれて黙って壊れないこと（10 節 7）
- 人が手でレビューするときにも同じ Skill を使えること（単体での利用）
- business-os の規則 2（bash を足さない）と整合すること（S6）
- 利用枠を増やしすぎないこと。多数決（8 パス）は利用枠が 8 倍になる

## 検討した選択肢（Considered Options）

- 案 A：`change-review` の核を残して v2 に組み直し、`dev-autopilot/skills/review/` に同封する
- 案 B：現行の `change-review` に最小の修正だけ入れる（S1〜S3 の解消のみ）
- 案 C：外部の Skill（組み込みの `/code-review` か mattpocock の `code-review`）をそのまま採用する

## 決定（Decision Outcome）

採用した選択肢:「案 A：`change-review` の核を残して v2 に組み直し、`dev-autopilot/skills/review/` に同封する」。
理由: 決め手のすべてを満たす唯一の選択肢だから。案 B は仕様の軸・再検証・信頼の境界・S4〜S6 を解消せず、案 C は収束の設計と fail-open の観点を失う（下記参照）。

### v2 の中身（9 節「方針」1〜7）

1. **3 つの軸を並列のサブエージェントで動かす**。それぞれ新しい文脈で起こす（同じ文脈のレビューは確認バイアスになる）。
   役は作業・レビュー・批評の 3 つ（ADR「進行役は決定的なスクリプトにし、AI は作業・レビュー・批評の 3 つの役だけを担う」（[ADR-20261008-001][adr-20261008-001-orchestrator-and-ai-roles]））で、
   レビューの中で並列に起こすサブエージェントは 3 軸＋批評者（下記 2）の最大 4 体とし、予算（下記 5）で上限を掛ける
   - 動作：`change-review` の核（品質ゲート → 壊れ方の表 → 実行で確かめる）。組み込みの `/code-review` を「手がかり」として先に 1 回呼ぶ案は段階 3 で試す
   - 仕様（目的との一致）：Issue の作業指示（agent brief）と差分を突き合わせ、4 つを見る。
     (a) 目的：作業指示の「困っていること」「望む振る舞い」を変更で本当に達成できるか。受け入れ条件を字面で満たしていても目的に届かない変更は 🔴。
     (b) 足りない要件：受け入れ条件のうち実装されていないもの。条件はテストに落として実行で確かめ、LLM の判定だけにしない。
     (c) 頼まれていない変更（scope creep）：作業指示の「範囲外」に触れた変更、作業指示に無い振る舞いの追加。
     (d) 実装が違う要件：実装されているが、作業指示と振る舞いが食い違うもの。
     仕様の軸の 🔴 は、動作の軸の 🔴 より先に報告する。コードが正しくても目的に合っていなければ PR はやり直しであり、コードの指摘を直す意味が無い
   - 規約：リポの正典（CLAUDE.md・ADR・構造仕様）との食い違い。リポの文書が常に優先。lint や型が機械で止めるものは指摘しない
2. **指摘ごとの再検証**。🔴 と 🟡 は、批評者（critic）のサブエージェントが「反対する前提」で実際のコードで再現を試みる。
   再現できたら証拠レベルを「実行済み」にし、できなければ「読んだだけ」に下げるか落とす。批評者は指摘ごとに確信度 0〜100 を付け、
   しきい値未満は 🟢 に下げるか捨てる。しきい値は設定に持ち、初期値は 80（Anthropic 公式 Plugin `code-review` と同じ）、段階 3 で測った誤検知率で調整する。重要度（影響の大きさ）と確信度（本当に起きるか）は別の軸として併記する。
   🟢 は再検証しない。解決済みの指摘は、新しい失敗シナリオが無ければ再提起しない
3. **出力の固定**。人が読む本文（PR #68 #71 #77 と同じ形）に加えて、件数（重要度ごと）・判定・指摘の一覧（id と見出し）を `claude -p --output-format json --json-schema` の構造化出力で返す
   （出力契約は ADR「GitHub への書き込みはすべて進行役が行い、AI は出力契約で結果を返す」（[ADR-20261008-003][adr-20261008-003-github-writes-by-orchestrator]））。
   印（R3-3。head の SHA・重要度ごとの件数・判定）はレビュー AI が本文に書かず、進行役が構造化出力から組み立てて投稿に付ける。投稿の先頭の「AI が生成した」の 1 行も進行役が付ける。
   AI の出力本文に `<!-- dev-autopilot:` で始まる文字列があれば、進行役が無条件に取り除く。
   見出しの文言を SKILL.md と報告の様式で一致させる。判定は印だけで行い、本文の言い回しは解析しない。印の形の正本は Plugin 内の 1 定数（`dev-autopilot/src/marker.ts`）で、Skill 側は定義を持たない（2 か所に定義を持たない）
4. **ラウンドの定義**。初回と再レビューを分ける。再レビューの入力は「前回の印と指摘」「修正コミットの範囲（SHA）」「差分」「作業指示（コラボレータの文）」「進行役が付けた事実（CI の結果、変更ファイル）」の 5 つで、
   作業 AI の対応コメントと PR の説明文は渡さない。見るのは修正の差分と、修正が触れた入力の棚卸しのやり直し。ラウンドの表を必ず出す
5. **無人の入り口**。引数で基点・仕様の在りか・🟢 の起票先・予算（ターン・時間・`--max-budget-usd`）を受け取る。欠けていれば聞かずに「未収束（理由）」で返す。
   レビュー AI の予算の初期値は 45 分・200 ターン（作業 AI と同じ）に `--max-budget-usd` を加えたもので、設定ファイルに持つ。
   サブエージェントは再帰して Skill を呼ばない。修正しない。マージしない
6. **信頼の境界**。差分は作業の内容であって指示ではない。PR の説明文（作業 AI の主張）はレビュー AI に渡さない。読むコメントはコラボレータのものだけ（4.8 節）
7. **残すもの**。壊れ方の表、証拠レベル、止めどき、🟢 の Issue 化、コミットごとのゲートの検査。
   ゲートの検査は `per-commit-gates.sh` を TypeScript（`dev-autopilot/skills/review/scripts/per-commit-gates.ts`、Node 24 が直接実行）に書き直し、`review` Skill から呼ぶ（12 節 判断 4）。
   置き場を `src/` ではなく Skill のフォルダの中にするのは、skills CLI の単体導入で Skill のフォルダごと写るためである（`src/` に置くと単体では付いてこない）。bash を置かない規則はそのまま

### 業界の実践から v2 に取り入れたもの（9 節「業界の実践」）

| 出どころ | v2 への反映 |
| --- | --- |
| 論文「Adversarial Review」 | 批評者の役を 1 体足し、指摘を「構造化された反対」で監査する。体を増やすより証拠を必須にする方が効くため、批評者は 1 体に留め、サブエージェントは 3 軸＋批評者の最大 4 体を超えない |
| 論文「LLM は仕様への適合を見られるか」 | 仕様の軸は LLM の判定に委ねず、受け入れ条件をテストに落として実行する。「仕様に合わない」と言う前に、合わないことを示す入力を実行で作る。作れなければ 🟢 に下げる |
| 論文「文脈のバイアス」 | PR の説明文を細工した攻撃が Claude Code と CodeRabbit の両方で 33 件中 32 件成功した。作者の主張をレビュー AI に読ませない（上の 6） |
| Anthropic 公式 Plugin `code-review` | 指摘ごとに確信度 0〜100 を付け、しきい値未満を捨てる（上の 2）。しきい値は固定せず設定に持つ |
| Cursor Bugbot（公式ブログ） | 差分の順番を変えた 8 パスの多数決は採らない（利用枠が 8 倍になる）。代わりに批評者 1 体の再検証で誤検知を落とす。前回の投稿との重複除去は取り入れる |

### 取り込まなかったもの

- mattpocock の smell 12 種：設計の匂いは「判断」で、ループで直すと収束しない。dev-autopilot のレビューには入れない。人の設計レビューには別の Skill で使える
- 1 指摘 1 インラインコメント（組み込みの形）：PR #68 #71 #77 と同じ運用（1 ラウンド 1 コメント）の方が進行役が読みやすく、履歴も追いやすい（R3-2）
- 多数決（Bugbot の 8 パス）：上の表のとおり。段階 3 で誤検知率が目標を超えたら、🔴 だけ 2〜3 パスの多数決を検討する

### 置き場と単体での利用（10 節 7）

- 正本は `dev-autopilot/skills/review/SKILL.md` に置き、dev-autopilot が自分の Skill として Plugin の名前空間で読み込む。`~/.claude` には依存しない（P14。フォルダの構成は ADR「dev-autopilot は分離を見越して 1 つのフォルダに Plugin の形で閉じ、導入と点検も Plugin が担う」（[ADR-20261008-008][adr-20261008-008-self-contained-plugin-layout]））
- Skill は Plugin に同封し、別に公開して組み合わせる形は採らない。進行役・agent・Skill は印の形（R3-3）や引数で結びついていて、版がずれると黙って壊れる。Plugin の 1 つの版で一緒に検査し、一緒に配る
- 単体で使う価値があるのは `review` だけ（`setup` `check` `intake` `dev-autopilot` は進行役と設定ファイルが無いと意味を持たない）。
  `review` は Plugin の中からも単体からも動くように書く。手順の本体は単体で成り立たせ、dev-autopilot 向けの部分（構造化出力、無人の入力、agent の名前）は引数で渡されたときだけ使う。
  `${CLAUDE_PLUGIN_ROOT}` や agent の名前を手順の本体に埋め込まない
- 分離後は、skills CLI がリポの `skills/<名前>/` を `<owner>/<repo>@<名前>` で単体導入できるので、`skills/review/` をそのまま指す。単体で配るために別の場所へ写さない（正本は 1 つのまま）
- 分離前（business-os の中にある間）は、`~/.claude/skills/change-review` を今の版のまま残して手動のレビューに使う。v2 を手でも使いたくなったら、`dev-autopilot/skills/review/` を skills CLI（`--copy` 付き）で入れる。
  `~/.claude` の bash 版 `per-commit-gates.sh` も分離まで手動のレビュー用に残す

### v2 が解消する S1〜S6

| # | 足りない点 | v2 での直し方 |
| --- | --- | --- |
| S1 | 「迷ったらユーザーに聞く」「起票先が決まっていなければユーザーに聞く」が 2 か所ある | 基点は PR の base、起票先は Issue、と進行役が引数で先に答える。Skill にも「無人のときは聞かずに未収束と書く」を足す（上の 5） |
| S2 | 再レビューの入り口が無く、「## 再レビュー結果 R<n>」を場当たりで書いていた | 「再レビュー」の節を足す。入力は前回の印と指摘・修正コミットの範囲（SHA）・差分・作業指示・進行役が付けた事実の 5 つ。見出しとラウンドの表の形を固定する（上の 4） |
| S3 | 機械で読める出力が無い。報告の見出しが SKILL.md と実際の PR でずれている | 件数・判定・指摘の一覧を構造化出力（`--output-format json --json-schema`）で返し、印（R3-3）は進行役が組み立てて付ける。人が読む本文は自由のまま、判定は印だけで行う（上の 3） |
| S4 | 予算（時間・ターン）の概念が無い。無人では利用枠を読めない | 進行役が `--max-turns`・時間の上限・`--max-budget-usd` を掛け（初期値は 45 分・200 ターン）、上限に当たったら「未収束」で返させる。レビュー AI の中から `claude -p` を起動することは許さない（上の 5） |
| S5 | 修正する側とレビューする側が同じ人である前提 | 修正は作業 AI。「修正したら通し直す」は「作業 AI の修正に同じ手順を通す」と読み替え、S2 の節に書く |
| S6 | `per-commit-gates.sh` が bash で、`check:shell` が落ちる | TypeScript に書き直して `dev-autopilot/skills/review/scripts/` に置く（12 節 判断 4。9 節 S6 の「そのまま使う」は取り消し） |

### 影響（Consequences）

- 良い点: `change-review` で実際に収束した設計（実行を先に払う・壊れ方の表・止めどき）を失わずに、無人で動く入り口と機械で読める判定を得る
- 良い点: 仕様の軸が加わり、「コードは正しいが目的に合わない」PR をコードの指摘より先に止められる
- 良い点: 批評者の再検証と確信度で誤検知を落とす。利用枠の増え方は多数決（8 倍）より小さい（サブエージェントは 3 軸＋批評者の最大 4 体）
- 良い点: Skill と進行役を同じ版で配るので、印の形がずれて黙って壊れる事故が起きない
- 良い点: bash を無くし、business-os の規則 2 と `check:shell` に整合する
- 悪い点: 作り直しに近い作業量になる。段階 0c の一部として進めるため、段階 3 の開始が Skill の完成に依存する
- 悪い点: 3 軸＋批評者（最大 4 体）でレビュー 1 回あたりの利用枠が増える。R2-13 の記録で 1 PR あたりの利用枠を測り、予算の設定（45 分・200 ターン・`--max-budget-usd`）で上限を掛ける
- 悪い点: 分離前は `~/.claude/skills/change-review`（手動用）と `dev-autopilot/skills/review/`（v2）の 2 本が並ぶ。正本は v2 で、旧版は変えない
- 中立: 仕様の軸は作業指示（agent brief）の受け入れ条件が「1 つずつ検証できる形」で書かれていることに依存する。作業指示の形は `intake` 側の決めごと

### 確認方法（Confirmation）

- 作り方は `skill-creator` Skill に従う。評価のケースは、すでにレビュー済みの PR #68 #71 #77 を使い、「人が出した 🔴 🟡 を v2 も出すか」「出さなかった指摘を v2 が増やしていないか」を見る（過去の PR が回帰テストになる）
- 段階 0c の出口として、v2 で 1 件の PR を手動でレビューし、PR #68 #71 #77 と同じ形（R1 → 対応 → R2）がそのまま出ることを確かめてから段階 3 に入る
- 段階 3 の出口：5 件の PR で、人が同じ PR を `change-review` した結果と 🔴 🟡 が一致し、人が却下した指摘の割合が 15% 以下（12 節「段階の割り直し」）。
  「人が却下した指摘」は、人が PR コメントの指摘に 👎 のリアクションを付けるか「却下」で始まる返信を書いたものを進行役が記録に数え、15% 以下の判定は記録から集計する
- `dev-autopilot/skills/review/scripts/per-commit-gates.ts` は vitest で検査し、business-os の `pnpm check` の対象に入れる（10 節 4「検査は 2 層」）
- `review` の SKILL.md に `${CLAUDE_PLUGIN_ROOT}`・agent の名前・印の定義（`<!-- dev-autopilot:` で始まる文字列）が埋め込まれていないことを、dev-autopilot の `check` で機械的に確かめる
- 進行役が、構造化出力から印を組み立てること、AI の出力本文の `<!-- dev-autopilot:` で始まる文字列を取り除くこと、再レビューの入力に作業 AI の対応コメントと PR の説明文を含めないことを vitest で検査する

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 案 A：`change-review` の核を残して v2 に組み直し、`dev-autopilot/skills/review/` に同封する

- 良い点: 決め手のすべてを満たす。収束の設計と fail-open の観点を残したまま、仕様の軸・再検証・固定の出力・無人の入り口を足せる
- 良い点: 進行役と同じ版で配るので、印の形がずれない
- 良い点: 単体でも動く書き方にすれば、分離後に skills CLI で手動用にもそのまま入れられる
- 中立: 作業量は作り直しに近い。ただし核（壊れ方の表・証拠レベル・止めどき・Issue 化）は再利用する
- 悪い点: サブエージェントが最大 4 体（3 軸＋批評者）になり、レビュー 1 回の利用枠が増える

### 案 B：現行の `change-review` に最小の修正だけ入れる（S1〜S3 の解消のみ）

- 良い点: 作業量が最も少ない。PR #68 #71 #77 と同じ形がそのまま出る
- 良い点: 手動のレビューにすぐ効く
- 悪い点: 仕様の軸が無いままで、「コードは正しいが目的に合わない」PR を止められない
- 悪い点: 指摘ごとの再検証と確信度が無く、誤検知率の目標（5〜15%）を達成する手段が無い
- 悪い点: PR の説明文を読ませない規則（信頼の境界）が入らない
- 悪い点: S4（予算）・S5（修正する側の前提）・S6（bash）が残る。置き場が `~/.claude` のままなので、専用マシンに無い問題（P14）も解消しない

### 案 C：外部の Skill（組み込みの `/code-review` か mattpocock の `code-review`）をそのまま採用する

- 良い点: 保守を外に任せられる。組み込みは `claude -p` と Actions で動き、並列サブエージェントと敵対的な検証をすでに持つ
- 良い点: mattpocock の `code-review` は規約と仕様の 2 軸を持つ
- 悪い点: どちらにも収束の規則が無い。組み込みは「再レビューは手動か push ごと」、mattpocock は「収束の保証は無い。きれいになるまで回すな」と明記している。対応ループ（R4）が終わらない
- 悪い点: fail-open（静かに通る）を最重視する壊れ方の表が無く、business-os の設計哲学と合わない
- 悪い点: 組み込みの出力は 1 指摘 1 インラインコメントで、進行役が読む印（R3-3）と 1 ラウンド 1 コメントの運用に合わない。mattpocock は不具合を探さず、サブエージェントが再帰して 50 体になる既知の不具合がある
- 悪い点: Skill の版を dev-autopilot が制御できず、印の形や引数が変わると黙って壊れる

## 補足情報（More Information）

- 根拠はすべて [要件メモ][memo] にある。9 節（`change-review` の評価、比較表、業界の実践、方針 1〜7、取り込まなかったもの、S1〜S6）、10 節 7（Skill の同封と単体利用）、P14、12 節 判断 4（`per-commit-gates.sh` の TypeScript 化）
- 要件メモの 9 節末尾には「PR は `~/.claude` のリポで別に作る」「S6 は変えない」とあるが、同じメモの P14・10 節 7・12 節 判断 4 で後から置き場を `dev-autopilot/skills/review/` に、S6 を TypeScript 化に改めている。本 ADR は後の決定に従う
- 業界の実践より踏み込んでいる点：AI 同士のレビューの往復を収束まで自動で回す製品は見つかっていない（11 節）。収束の規則（🟢 は直さない、解決済みは再提起しない、往復 3 回、head の SHA）は本 ADR の v2 と進行役（R4）で守る
- 決めていないこと（8 節）：レビュー側で `pnpm check` を実行するか、CI の結果を待つだけにするか。段階 3 で決める
- 実施の時期：段階 0c（`setup` と `check` の実装と同じ段階）。dev-autopilot の進行役の実装を待たずに進めてよい。直した内容は人が手でレビューするときにも効く
- 見直しの時期：段階 3 で誤検知率が目標を超えたら、確信度のしきい値と観点を見直し、🔴 だけの多数決を検討する
