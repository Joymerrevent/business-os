# 進行役の投稿にはすべて署名付きの印を付け、署名の対象に種類・リポ・番号を含め、印が無効化されていたら止める

[要件定義書][req]の D-8 と D-14 を決める。4.12 節と R3-5、R6-4 を補い、I9・I12 の「下書きを作らず `needs-human`」と `quarantine=found` の矛盾を解く。

## 背景と課題（Context and Problem Statement）

4.12 節の印は 6 種類（`intake` `intake-final` `plan` `review` `fix` `merge`）で、どれも「段を進めた結果」に付く。進行役はこのほかに、依存の待ち（R5-5）、触る範囲の重なりの警告（R5-3）、催促（R7-2b）、`needs-human` の理由（R2-7 ほか）、検疫で止めた理由（I9）のコメントも書く。これらには印が無い。
印が無いと 3 つの問題が起きる。

1. 「1 回だけ書く」コメント（待ち、警告、催促）を、GitHub の状態から「すでに書いた」と判定できない（手元の記録は判定に使わない。SF-9）
2. 人の固定の見出し（`## 却下` など）は「印の無い投稿」で見分ける（R6-4）ので、印の無い進行役の投稿が人の投稿に数えられる。検疫で止めた理由に外の人の本文を引用すると、その見出しが人の作業指示として採用される
3. I9・I12 は検疫で見つかったら「下書きを作らず `needs-human`」とするが、4.12 節の `intake` の印は `quarantine=found` の値を持つ。下書きを作らないなら、印を載せる場所が無い

また、署名の対象は「`sig` 以外のすべての欄」だが、印の種類・リポ・Issue や PR の番号は欄に無い。別の PR の `review` の印を写しても署名が通る。
さらに、進行役が投稿した印のコメントが編集や削除で無効になると「無いもの」として扱われ、`dropped_high` や `verdict=fix` のような「止める側」の印が消えると通過に倒れる。

## 判断の決め手（Decision Drivers）

- 状態の正は GitHub（SF-9）。1 回だけ書くコメントも GitHub から判定する
- 人の投稿と AI の投稿を投稿者でなく印で見分ける（R3-5）
- 止める側の印が消えたときに通過に倒れない（fail-closed）

## 検討した選択肢（Considered Options）

1. 進行役の投稿すべてに署名付きの印を付ける。`note` の種類を足し、`kind` で用途を分ける。署名の対象に種類・リポ・番号を含める。進行役の印が無効化（編集・削除・署名不一致）されていたら `needs-human`
2. 「1 回だけ」の判定だけ手元の記録で行い、印は増やさない
3. 止める側の印だけ累計を次の印に持ち越す（`dropped_high` の累計など）

## 決定（Decision Outcome）

採用した選択肢:「1」。理由: 判定の正を GitHub に保ち、人と AI の投稿の見分けを 1 つの規則（印の有無）で済ませられる。

中身：

- 印の種類に `note` を足す。欄は `kind=wait|overlap|remind|stop|quarantine|escalate`、`ref=<Issue か PR の番号>`、必要なら `reason=<短い記号>`。置き場は Issue か PR のコメント。人の編集は許さない。読む人は進行役（同じ `kind` と `ref` の印があれば「すでに書いた」）
- 検疫で見つかったとき（I9、I12）は、下書きを作らず、`note kind=quarantine` の印付きコメントに検査の結果（種類）を書き、`needs-human` にする。`intake` の印から `quarantine=` の欄を外す（`intake` が投稿されるのは検疫を通ったときだけ）
- 進行役が投稿するコメントは、人向けの本文があってもなくても、必ず署名付きの印を 1 つ持つ。外の人の本文を引用するときは、引用の各行の先頭に `>` を付け、`##` で始まる行を見出しとして扱わない
- 署名の対象を「`sig` 以外のすべての欄」に加えて、印の種類、リポ（`owner/repo`）、置き場の番号（Issue か PR）とする。別の PR から写した印は署名が通らない
- 進行役が過去に投稿した印（同じ Issue・PR の中で進行役のアカウントの投稿）のうち、R3-5 の 3 条件を満たさないものが 1 つでもあれば、その Issue・PR を `needs-human` にし、`note kind=stop reason=marker-invalid` を書く。メンテナが自分の投稿を編集した場合も同じ（編集でなくコメントの追加で直す運用にする）
- `review` の印の `round` は 1 から欠けずに続くこと、`dropped_high` は PR の累計であることを判定の条件に足す（途中の印が消えても累計が残る）
- AI のセッションに前回の印を渡すときは、進行役が解析した値（round・件数・verdict）だけを渡し、印の生の 1 行は渡さない。AI の出力から印を取り除く処理は `marker.ts` の解析と同じ正規表現（空白の揺れを含む）で行う

### 影響（Consequences）

- 良い点: 1 回だけ書くコメントの重複が GitHub だけで止まる
- 良い点: 人の見出しの誤認（引用の見出し）と、印の写しによる偽装が塞がる
- 良い点: 止める側の印が消えても累計と欠番の検査で止まる
- 悪い点: 進行役のコメントの誤字をメンテナが直すと `needs-human` になる。直すときは新しいコメントで補う運用にする
- 悪い点: 印の種類が 7 つになり、`marker.ts` と 4.12 節の表が増える

### 確認方法（Confirmation）

- `marker.ts` の単体テストで、種類・リポ・番号を変えた印の署名が通らないこと、空白を変えた印が取り除かれることを検査する
- 結合テストで、待ちのコメントが 2 回の実行で 1 件しか付かないことを検査する

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 1. すべての投稿に印、種類・リポ・番号を署名、無効化で止める

- 良い点: 規則が 1 つ（印の有無と真正性）
- 悪い点: 印の種類と検査が増える

### 2. 「1 回だけ」は手元の記録で

- 悪い点: SF-9 に反する。記録を失うと毎日同じコメントが付く
- 却下

### 3. 累計の持ち越しだけ

- 良い点: 小さい変更
- 悪い点: 人の見出しの誤認と、印の写しの問題が残る
- 一部を採用（累計の持ち越しは 1 に含めた）
