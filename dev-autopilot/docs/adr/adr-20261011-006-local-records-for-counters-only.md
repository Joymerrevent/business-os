# 手元の記録を判定に使うのは、実行の失敗の回数・拒否後のモデル・累計の利用枠の 3 つに限り、記録が無ければ安全側に倒す

[要件定義書][req]の D-7 を決める。R1-5・SF-9 の「手元の記録は判定に使わない」に例外を定める。

## 背景と課題（Context and Problem Statement）

R1-5 と SF-9 は「状態の正は GitHub に置き、手元の記録は判定に使わない」とする。途中で死んでも GitHub から復旧するためである。
一方で、R2-13 の「同じ Issue で実行の失敗が 3 回続いたら `needs-human`」、I12 の「拒否の後は次回 `sonnet`」、R2-13 の「累計の利用枠が上限に当たったら `needs-human`」は、GitHub に痕跡が無い（実行の失敗は印を書かない）ので、手元の記録が無いと数えられない。
GitHub に数を書く案（Issue のコメントに `note` の印で残す）もあるが、実行の失敗のたびにコメントが増え、人の読む量が増える。

## 判断の決め手（Decision Drivers）

- 途中死から GitHub だけで復旧できること（SF-9）
- 実行の失敗の歯止め（3 回、累計の利用枠）が機能すること
- 記録を失ったときに fail-open にならないこと

## 検討した選択肢（Considered Options）

1. 上の 3 つだけ手元の記録で数える。記録が無い（マシンの入れ替え、記録の削除）ときは安全側に倒す：失敗の回数は「上限に達した」扱い、拒否後のモデルは `sonnet`、累計の利用枠は「上限に達した」扱い
2. 3 つも GitHub の印（`note`）に書く
3. 記録に頼らず、数えない（3 回の歯止めを捨てる）

## 決定（Decision Outcome）

採用した選択肢:「1」。理由: 3 つはどれも「進めない方向」にしか働かない数で、記録を失って安全側に倒しても害は「人の確認が 1 回増える」だけ。GitHub に書くと人の読む量が増える。

中身：

- 手元の記録で数えてよいもの：(a) 同じ Issue の連続した実行の失敗の回数、(b) 受け入れ AI の拒否の有無（次回のモデル）、(c) Issue ごとの累計の利用枠
- (a) の記録が無い Issue で実行の失敗が起きたら、1 回目でも `needs-human`。(b) の記録が無ければ `sonnet` で起動する。(c) の記録が無ければ、その Issue の次のセッションを起こさず `needs-human`（人が記録を復旧するか、上限を認めてラベルを外す）
- 記録が「無い」の判定：Issue の記録ファイルが無い、または破損している。実行の記録が 1 つも無い（初回）は「無い」に数えない（初回は失敗も累計も 0 から始める）
- 判定（次の段の決定、収束、マージ判定）には引き続き手元の記録を使わない。上の 3 つは「上限の数え上げ」であって判定ではない、と基本設計に書き分ける

### 影響（Consequences）

- 良い点: GitHub への書き込みを増やさずに歯止めが機能する
- 良い点: 記録を失っても fail-open にならない
- 悪い点: 記録を失うと、進行中の Issue が 1 回の失敗で `needs-human` になる。マシンの入れ替えでは記録フォルダも移す運用にする

### 確認方法（Confirmation）

- 単体テストで、記録が無いときの 3 つの分岐が安全側になることを検査する

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 1. 3 つだけ手元で数え、無ければ安全側

- 良い点: 例外が 3 つに限られ、どれも進めない方向
- 悪い点: マシンの入れ替えで記録を移し忘れると、人の確認が増える

### 2. GitHub の印に書く

- 良い点: 復旧が完全
- 悪い点: 実行の失敗のたびにコメントが増える。人の読む量が増える
- 却下

### 3. 数えない

- 悪い点: 同じ失敗を毎日繰り返し、利用枠を消費し続ける
- 却下
