# 要件が決めていない値は基本設計が「暫定」として持ち、設計の形を変える判断だけを ADR にする

[要件定義書][req]の D-12 と D-16 を決める。要件・ADR・設計書の分担を定める。

## 背景と課題（Context and Problem Statement）

要件定義書の 8 節には「未定」の値がある（1 回の実行の所要時間、受け入れの件数、セッションの費用、累計と 1 日の利用枠、再試行の間隔、Agent ツールの可否、批評者の確信度のしきい値、置き場）。検疫のしきい値（base64 の長さ、エスケープの数）のように要件が言及すらしていない値もある。
基本設計のレビューは、設計がこれらを決めたことを「要件に無い判断」として挙げた。しかし値は運用で変わるもので、変えるたびに ADR を起票すると ADR が値の変更で埋まる。
一方で、信頼の境界・状態モデル・役と段・段階と出口・マージ判定の条件のように設計の形を変える判断は、設計書で黙って決めてはいけない。

要件メモの 8 節から引き継いだ 4 つの論点（D-12）も、どこで決めるかを定める必要がある。

## 判断の決め手（Decision Drivers）

- ADR が「設計の形」の判断に絞られ、読む価値を保つ
- 値の変更が設定ファイルの変更だけで済む
- 値がどこで決まったかを後から追える

## 検討した選択肢（Considered Options）

1. 線引きを定める：設計の形を変える判断は ADR、値と実装の手順は設計書が「暫定」と明記して持ち、変更は設定ファイルで行う
2. すべての値を ADR で決める
3. すべて設計書で決める（ADR を使わない）

## 決定（Decision Outcome）

採用した選択肢:「1」。理由: ADR の粒度を「後から変えにくい判断」に合わせる。

中身：

- **ADR にする判断**：信頼の境界（誰が何を書けるか・読めるか）、状態モデル（Status・Agent 欄・ラベル・印の種類と意味）、役と段（AI の役の増減、段の増減と数え方）、段階と出口、マージ判定の条件（許可一覧の方針、判定の条件の増減）、AI に渡す文の扱い（検疫の対象と扱い）、記録の正の置き場
- **設計書で「暫定」として決めてよいもの**：上限・しきい値・間隔・日数・初期値、パスと置き場、検疫の見本の文字列、JSON スキーマの欄の名前、コマンドの形、API の取り方。設計書の設定の文書（config）に「暫定」の列を持ち、要件定義書の 8 節の「未定」の行は「設計の config を参照」と書く
- 暫定の値を変えるときは設定ファイルと設計書の config だけを変える。ADR は起票しない。ただし値の変更が ADR の決定の前提を崩すとき（例：許可一覧を広げる、WIP を 2 以上にする）は、該当する ADR の「追記」か新しい ADR で扱う
- D-12 の 4 つの論点の扱い：
  - レビュー側で `pnpm check` を実行するか：`review` Skill の核が「実行して確かめる」なので実行する。CI の結果はそれとは別に進行役が読む。設計書に書く（値ではないが、R3-1 の核の範囲内）
  - 記録の置き場：暫定の値（設計の config）
  - 自動化用のアカウントを分けるか：段階 3 で実機を見てから ADR で決める（要件 P9 のまま）
  - クラウドの仕組みの利用：段階 5 の出口を越えて専用マシンへの移行を決めるときに ADR で決める（要件メモ 8 節のまま）
- 設計レビューが挙げた値（実行時間 180 分、受け入れ 5 件、セッション 5 ドル、Issue 累計 20 ドル、日 30 ドル、再試行の間隔 1 回、確信度 80、Agent ツール不可、検疫のしきい値 base64 200 文字・エスケープ 20、メールの許可リスト、gitleaks の規則の利用）は、本 ADR の承認後に設計の config に「暫定」として写す

### 影響（Consequences）

- 良い点: ADR が設計の形の判断に絞られる
- 良い点: 値の変更が速い
- 悪い点: 「形」と「値」の線引きに迷う判断が出る。迷ったら ADR にする（要承認か迷ったら要承認、と同じ考え方）

### 確認方法（Confirmation）

- 基本設計の config の表に「暫定」の列があり、要件定義書の 8 節の「未定」の行がそこを参照していることをレビューで確かめる

## 選択肢ごとの長所と短所（Pros and Cons of the Options）

### 1. 線引きを定める

- 良い点: 粒度が揃う
- 悪い点: 線引きの判断が要る

### 2. すべて ADR

- 悪い点: 値の変更のたびに ADR が増え、形の判断が埋もれる
- 却下

### 3. すべて設計書

- 悪い点: 形の判断が設計書に埋もれ、後から変えにくい判断の記録が残らない
- 却下
