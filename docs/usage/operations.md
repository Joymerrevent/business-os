# 日々の運用

導入が終わった後、business-os をどう回すかを説明します。「はじめる」を先に読んでください。

## 考え方：5 つの仕事 × 4 つの周期

会社を運営するとは、突き詰めると 5 つの仕事です。

1. **方向を決める**：何をやるか、何をやらないか
2. **数字を見る**：お金が回っているか、事業ごとに儲かっているか
3. **期限を守る**：申告、支払い、契約更新。忘れると信用を失う
4. **記録する**：なぜそう決めたか。後から自分を助ける
5. **振り返って直す**：うまくいかないことをやめ、繰り返す作業を仕組みにする

business-os はこれを日・週・月・四半期の周期に割り付けます。

| 周期 | Skill | 何をするか |
|---|---|---|
| 毎日 | `/morning` | 今日の優先 3 件、承認待ち、今日の期限 |
| 毎週 | `/weekly-review` | 今週の実績、来週の重点、事業ごとの時間配分 |
| 毎週 | `/check` | 安全装置と文書の点検 |
| 週次 or 月次 | `/retro` | 振り返りから、business-os と運用への改善提案 |
| 毎月 | `/close` | 月次締め。事業別の収支、資金の見通し、来月の期限 |
| 四半期 | `/quarterly` | 各事業を続けるか、縮めるか、やめるか |
| 随時 | `/adr` | 重要な判断を記録する |
| 随時 | `/validate` | 新しいことを始める前に、仮説と撤退条件を決める |
| 随時 | `/approve` | CC の提案を確認して反映する |

## 日次

朝、`claude` を開く前に、`company` で `git pull` を自分で実行してください。別の端末で変えた内容を取り込むためです。

`git pull` のほか、`git checkout` `git merge` `git stash` `git rebase` のように作業中のファイルを書き換える
git 操作は、CC に頼まずあなたが行ってください。CC の安全設定は、CC が起動するコマンドから憲章
（`docs/charter/`）への書き込みを禁じているため、CC 経由ではこれらの操作が途中で失敗します。
CC が行う git 操作は commit と push だけです。

`company` で `claude` を開き `/morning`。出力は次の 5 項目です。

- 全社サマリ（1 行）
- 今日の優先事項（最大 3 件）
- 承認待ち（件数と緊急度）
- 今日と直近の期限
- あなたへの問い（未確定のことがあれば）

「あなたへの問い」は、答えられるならその場で答えてください。答えると憲章や台帳に反映され、
翌日から同じ問いは出ません。答えないと毎朝出続けます。「決めない」を「決める」のも一つの答えです。

日中に CC へ頼んだ作業は、自動で日報（`docs/operations/daily/`）に 1 行ずつ記録されます。
これが週次の振り返りと、Skill 化の判定材料になります。

## 週次

### `/weekly-review`

今週の日報と事業別の現況を読み、実績・来週の重点・時間配分を整理します。
「どの事業に何時間使ったか」を聞かれるので、おおよそで答えてください。
複数事業を並走させると、時間の偏りが数字より先に問題を教えてくれます。

### `/check`

business-os の安全装置が「存在するか」ではなく「効いているか」を試験します。
結果は pass / warn / fail で `docs/operations/reviews/` に残ります。fail が出たら、
表示された対処を先に済ませてください。安全装置が壊れた状態で運用を続けないためです。

`/check` は、本物の Claude Code で安全装置が実際に動くかの試験（発火試験）もするか聞きます。
試す場合は、CC が示す `!` から始まる 1 行を、入力欄でそのまま実行してください。
あなたの会社のデータの一時的な複製で試すので、データそのものには触れません。利用枠を消費し、所要は数十秒です。

### `/retro`

日報とレビューを読み、次の 3 種類を提案します。

- 同じ依頼が 2 回以上あった作業の Skill 化
- 使われていない Skill の削除・凍結
- 地図（`CLAUDE.md`）や運用ルールへの追記

提案は `docs/proposals/` に置かれ、`/approve` で承認すると反映されます。
慣れるまでは月に 1 回でも構いません。

## 月次

### `/close`

月初に実行します。今月の週次レビューと、手元の数字を突き合わせます。

- 事業ごとの売上・費用・差額
- 全社の資金残高と、来月の支払い予定
- 来月の期限一覧

数字は正確でなくても構いません。ただし**「いつ時点の数字か」（データ基準日）は正確に**答えてください。
business-os は全ての数字に基準日を付けて記録します。3 ヶ月後に読み返したとき、
「これは 9 月末の数字だ」と分かることが、数字そのものの精度より大切です。

### 剪定

`/retro` が「先月使わなかった Skill」を挙げます。迷ったら消してください。
必要になればまた作れます。増える一方にしないことが、business-os を軽く保つ唯一の方法です。

## 四半期

`/quarterly` は 3 ヶ月分の月次締めを読み、事業ごとに問います。

- 続けるか、縮めるか、やめるか
- 憲章に書いた方針は、まだ正しいか

憲章の各文書には「最終確認日」があります。90 日を超えたものは、ここで「まだ正しい」か
「変える」かを聞かれます。変える場合は CC が提案を書き、`/approve` で反映します。

週次だと目の前のことしか見えません。3 ヶ月に 1 回、強制的に「この事業、続ける？」と問う場を
持つことが、複数事業を運営する上で最も効きます。

## 承認の仕組み

CC は、会社の方針（憲章）と外部に影響が出る行動を、勝手に確定しません。
提案を書き、あなたの承認を待ちます。

1. CC が `docs/proposals/` に提案を書く（背景・変更内容・差分・根拠の日付）
2. あなたが `/approve` → 提案の一覧と差分が出る → 「承認」「却下」「修正」を答える
3. 承認すると CC が反映する。その瞬間に CC の権限確認が 1 回出るので「はい」と答える
4. 提案ファイルは履歴として残る

あなたの判断は 2 回（承認、権限確認）。これが承認疲れしない最小回数です。

承認が要るのは 2 種類だけです。それ以外（日報、レビュー、調査メモ）は CC が直接書きます。

- 外部に影響が出る行動：送信、投稿、支払い、公開
- 憲章と地図の変更

## 提案と決定記録の使い分け

- **提案（proposals）**：憲章を変えたい、外部行動をしたい。承認待ち
- **決定記録（decisions）**：重要な判断をした事実と理由。`/adr` で起票。承認は不要だが、
  「accepted」に変えるのはあなた

両方とも ID は `日付-連番`（例 `20261015-01`）です。ファイル名を見れば、いつの判断か分かります。

## 記録と日付の作法

business-os が作る全ての文書には 4 つの日付が付きます。

| 欄 | 意味 |
|---|---|
| created | このファイルを書いた日 |
| updated | 最後に内容を変えた日 |
| as_of | 中身の数字・事実が「いつ時点」のものか |
| verified | 人間が「まだ正しい」と確認した日 |

該当しない欄は `n/a` と書かれます。空欄はありません。空欄があると「忘れた」のか「該当なし」なのか
区別できないためです。

日付は必ず `2026-10-05` の形です。「昨日」「先週」は使いません。1 ヶ月後に読むと意味が変わるからです。

CC は、古い情報で判断するとき「この情報は 45 日前のものです」と必ず告げます。黙って使いません。

## 業務 Skill を育てる

business-os に入っている 10 個の Skill は「どんな会社でも要るもの」です。あなたの事業に固有の作業は、
最初は CC に普通に頼んでください。

同じ依頼が 2 回目になると、`/retro` が「これを Skill にしますか」と提案します。
承認すると `company/.claude/skills/` に Skill ができ、次から 1 コマンドで呼べます。
business-os の更新で消えることはありません。

Skill を先に設計しないでください。使ってから、繰り返したものだけを Skill にする。この順番が、
business-os が使われなくなる最大の原因（作ったが動かしていない）を防ぎます。

## business-os の更新

business-os は Plugin として更新されます。新しい版を取り込むには `/plugin marketplace update business-os` を実行します
（`/plugin` の「Marketplaces」で自動更新を有効にすることもできます）。更新後、最初のセッションで
「business-os が更新されました。`/onboard --migrate` を実行してください」と表示されることがあります。
雛形の差分をあなたの `company` に反映するためです。事業データは触りません。

## 手動から自動へ

周期 Skill は、最初はあなたが手で呼びます。2〜4 週間続いて `/retro` が「毎回呼んでいる」と
確認したものから、決まった時刻に自動で走らせる設定（Routines）に移せます。

最初から自動にしない理由は一つです。自動で出た結果は読まれなくなるからです。

## よくある失敗

| 症状 | 対処 |
|---|---|
| 入れたが使っていない | `/morning` だけ毎朝やる。他は要らない |
| 承認が溜まって面倒 | 承認対象が 2 種類を超えていないか `/check` で確認。超えていたら憲章の判断ルールを見直す |
| 古い数字で判断していた | business-os は日付を告げている。読み飛ばさない。`/close` を月初にやる |
| Skill が増えすぎた | 月次剪定。迷ったら消す |
| 憲章を CC が書き換えた | 起きない設計。起きたら `/check` を実行し、Issues に報告 |
