# 20260929-07: 経営基盤 Skill は最初から、業務 Skill は育てる

## 背景

作った機能の大半は使われない。gstack は 35 コマンドを持つが、1 ヶ月使ったレビュアーが
定着させたのは 6 つ。FounderOS の主催者は「インストールしたが運用に乗っていない」人と
30〜40 件相談してワークショップを作った。最初から全部作ると、使われない 8 割のメンテコストと
認知負荷が、使う 2 割の価値を食う。

一方で、「会社を運営する以上どんな事業でも必要なもの」は最初から無いと、運営自体が回らない。
この 2 つを区別する。

## 決定

### Skill は 2 種類

- **経営基盤 Skill**：事業非依存。会社を運営する以上必ず必要。**business-os に最初から入れる**
- **業務 Skill**：事業固有の作業。business-os に入れず、**使いながら育てる**

### 経営基盤 Skill（10 個、固定）

会社運営を「方向を決める / 数字を見る / 期限を守る / 記録する / 振り返って直す」の 5 つの仕事に分解し、
「日・週・月・四半期」の周期で回す。

| 分類 | Skill | 役割 |
|---|---|---|
| business-os の運転 | `/onboard` | 事業情報のインタビュー注入 |
| business-os の運転 | `/approve` | 承認パイプライン |
| business-os の運転 | `/check` | 週次の重い点検 |
| 経営の記憶 | `/adr` | 意思決定の記録 |
| 日次 | `/morning` | 今日の優先事項、承認待ち、今日の期限 |
| 週次 | `/weekly-review` | 今週の実績、来週の計画、時間配分 |
| 月次 | `/close` | 月次締め。事業別の収支、資金の見通し、来月の期限 |
| 四半期 | `/quarterly` | 各事業の継続 / 縮小 / 撤退、戦略の見直し |
| 改善 | `/retro` | 振り返りから business-os と運用への改善提案 |
| 施策ゲート | `/validate` | 新施策を始める前の仮説検証 |

### 参照ドキュメントの雛形（3 種、`/onboard` で初期値を入れる）

- 期限・義務台帳（`operations/obligations.md`）：税務、支払い、契約更新、許認可
- 事業別の現況（`operations/state/<事業ID>.md`）：動いているもの、待ち、詰まり
- リスク台帳（`operations/risks.md`）：各事業を止めかねない要因と兆候

### 業務 Skill の育て方

- **2 回ルール**：同じ作業を CC に手で頼んだのが 2 回目になったら Skill 化を検討する。
  検出と提案は `/retro` が行う（人間が数えない）
- **月次剪定**：先月使わなかった Skill は削除か凍結。増える一方にしない
- 判定材料は日報の実行記録（全 Skill が当日の daily に 1 行追記する）

### 周期 Skill の起動

最初は人間が手で呼ぶ。2〜4 週間で習慣がつき、`/retro` が「毎回呼んでいる」と確認できた Skill から
Routines（スケジュール起動）に移す。

## 根拠

- 「最小から始めて使った分だけ育てる」は先行事例の失敗分析から最も強く支持される原則
- ただし利用者（会社運営の経験がない）が「何が必要か」を自分で判断するのは難しい。
  経営基盤 10 個は「一般的な経営管理で必ず要るもの」を第三者目線で固定したもの
- 3 回ではなく 2 回にしたのは、Skill を作るコストが低く、外れても月次剪定で捨てられるため
- 自動起動を後回しにするのは、「結果を誰も読まない」状態を避けるため
- 検討した代替案：`/onboard` `/approve` `/check` の 3 つだけで始める → 会社運営に必要な
  記録・振り返り・数字の場が無く、運営が回らない。不採用

## 影響

- business-os の Skill 数は 10 で固定し、business-os のリリースで増やさない。増やしたい場合は ADR で議論する
- 業務 Skill は `company/.claude/skills/` に置く（business-os の外）。business-os の更新で消えない
- `/retro` が business-os の改善提案を出す（20260929-05 の承認経由）。business-os が自分で育つ仕組みの中核
- `/close` と `/quarterly` は数値を扱うため、`as_of`（データ基準日）を必須にする（20260929-09）
