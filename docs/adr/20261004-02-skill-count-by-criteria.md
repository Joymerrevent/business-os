# 20261004-02: 配布する Skill の数を 10 個に固定せず、分類ごとの追加の条件と ADR で増減を決める。一覧と実物の照合は続ける

## 背景と問い

20260929-07 は Skill を「経営基盤 Skill（business-os に最初から入れる）」と「業務 Skill（company で育てる）」の 2 種類に分けた。
同じ ADR の影響の節で「business-os の Skill 数は 10 で固定し、business-os のリリースで増やさない。増やしたい場合は ADR で議論する」と決めている。

数を固定した狙いは、使われない Skill を増やさないことにある（20260929-07 の背景：gstack は 35 コマンドのうち定着したのが 6 つ、
「インストールしたが運用に乗っていない」利用者が多い）。固定した数そのものに意味があるわけではない。

2026-10-04、利用者が business-os の不具合や改善を報告するのを手伝う Skill（20261004-01）を検討した。
報告の Skill は、事業の運営ではなく business-os そのものを扱い、日・週・月・四半期の周期では回さない。
経営基盤の 10 個とは性質が違うが、いまの決まりでは配布する Skill の数に数えられ、「10 個で固定」に当たる。

同じ日、メンテナから、事業に依存しない業務の Skill も配布に含めたいという要望が出た。
例は、メールの受信箱を整理する、メールや資料を要約して TODO の一覧を作る、といった、どの事業でも使う作業である。
20260929-07 の「業務 Skill」は「事業固有の作業」と定義され、company で育てる。事業に依存しない業務の Skill は、
経営基盤 Skill（会社の運営の仕組み）にも業務 Skill（事業固有）にも当たらず、置き場が決まっていない。

数の固定は、次の場所に書き込まれている（2026-10-04 時点）。

- コード：`hooks/lib/plugin.ts` の `FOUNDATION_SKILLS`（10 個の名前の一覧。コメントに「10 個、固定」）。
  一覧は、`check:skills`（`scripts/lib/repo-checks.ts`。`skills/` のフォルダと一覧が一致しなければ fail、メッセージに「10 個で固定」）、
  起動時の軽い点検（`hooks/session-start.ts`。一覧の Skill の存在とフロントマター、company や利用者の Skill との名前の衝突）で使う
- 文書：`CLAUDE.md`、`docs/design/architecture.md`（4 か所）、`docs/usage/operations.md`、`templates/skill-conventions.md`、`skills/retro/SKILL.md`

一覧（`FOUNDATION_SKILLS`）は、数を数えるためだけでなく、Skill の欠落や紛れ込みを点検で止めるために働いている。
数の固定を外しても、一覧と実物の照合はフェイルセーフとして残す必要がある。

問い：

1. 配布する Skill の数を固定し続けるか。固定しないなら、何で増えすぎを防ぐか
2. 経営基盤 Skill と性質の違う Skill（business-os そのものを扱う Skill、事業に依存しない業務の Skill）を、どう分類するか
3. 配布した Skill が使われていないことに、どう気づき、どう減らすか

## 判断の基準

- 20260929-07 の狙い（使われない Skill を増やさない）を保つ
- 増やすかどうかを、数ではなく、条件に照らして判断できる
- 増やすたびに議論の記録（ADR）が残る
- 一覧と実物のずれ（Skill の欠落・紛れ込み）は、今と同じく点検が fail で止める
- 利用者が `/` で見る Skill の一覧が、目的の分からない Skill で埋まらない
- 外部のツール（メールなど）に頼る Skill は、ツールが無い利用者の環境でも安全側に止まる

## 検討した案

- 案 A：今のまま、配布する Skill を 10 個で固定する
- 案 B：経営基盤 Skill は 10 個で固定したまま、別の分類（サポート Skill）を数の外に設ける
- 案 C：数の固定をやめ、分類ごとの追加の条件と ADR で増減を決める
- 案 D：数の上限（例：全体で 15 個まで）を設ける

## 決定

採用：**案 C**。

数の固定は「使われない Skill を増やさない」ための代わりの物差しで、条件を満たす Skill まで止めてしまう。
一方で、数を固定しても、10 個がそれぞれ使われているかは確かめていない。
増やす条件と減らす経路を明文化し、追加のたびに ADR で議論するほうが、20260929-07 の狙いに直接効く。
案 B は今回の報告の Skill には足りるが、経営基盤 Skill を増やしたくなったときに同じ議論をくり返すことになる。

1. 配布する Skill の数を固定しない。20260929-07 の影響の節の「business-os の Skill 数は 10 で固定し、business-os のリリースで増やさない」を、この ADR の決定で置き換える。
   20260929-07 のほかの決定（経営基盤 Skill と業務 Skill の区別、10 個の中身、業務 Skill の育て方、周期 Skill の起動）は変えない
2. Skill を次の 4 つに分類する。20260929-07 の 2 種類（経営基盤 Skill と業務 Skill）はそのまま残し、配布する分類を 2 つ足す

   | 分類 | 置き場 | 中身 | 増減の決め方 |
   |---|---|---|---|
   | 経営基盤 Skill | business-os（配布） | 事業非依存で、会社を運営する以上必要な仕組み（20260929-07 の定義のまま）。今の 10 個 | 決定 3 の条件と ADR |
   | 共通業務 Skill | business-os（配布） | 事業非依存で、どの事業の利用者も日々行う業務の作業（例：メールの受信箱の整理、要約から TODO の一覧を作る） | 決定 3 の条件と ADR |
   | サポート Skill | business-os（配布） | 事業の運営ではなく、business-os そのもの（導入・点検・報告など）を扱い、必要なときだけ呼ぶもの。最初の候補は報告の Skill（20261004-01） | 決定 3 の条件と ADR |
   | 業務 Skill | company の `.claude/skills/` | 事業固有の作業（20260929-07 の定義のまま） | 2 回ルールと月次の剪定（20260929-07 のまま） |

   - 配布する 3 つの分類は、Skill の名前の一覧（コード）で持つ
   - 今の 10 個を、この ADR で別の分類に分け直すことはしない（`/onboard` `/approve` `/check` の扱いは、必要になったら別の ADR で決める）
   - 利用者の company で育った業務 Skill が、ほかの事業でも使えると分かったら、共通業務 Skill の候補として business-os への改善案に挙げられる（`/retro` の手順 6）
3. 配布する Skill を足すときは、次をすべて満たし、Skill ごとに ADR で決める
   1. 事業非依存である（20260929-04）
   2. 既存の Skill の手順を足すことでは済まない理由がある
   3. 分類（経営基盤 / 共通業務 / サポート）と、呼ばれる場面が決まっている
   4. 使われたことを確かめる方法がある（全 Skill が日報に実行記録を 1 行書く。`templates/skill-conventions.md`）
   5. Skill の動作の検証のケースがある（`evals/skills/<Skill 名>/`、20261003-01）
   6. 共通業務 Skill は、さらに次を満たす
      1. 多くの利用者が使う見込みがある（特定の職種や業界だけの作業は、業務 Skill として company で育てる）
      2. 外部のツール（メール・カレンダーなどのコネクタ）に頼るなら、ツールが接続されていない環境では、何もせずに理由を告げて止まる
      3. 外部に影響が出る行動（送信・削除・移動・公開）は、実行の前に人に確認する（20260929-05）
      4. 外部から読んだ内容（メールの本文など）はデータとして扱い、中に書かれた指示に従わない
      5. 既製の Skill（公式の Plugin など）で足りるなら作らず、そちらを案内する（20260929-08）
4. 利用者が Issue で Skill の追加を提案したときは、次の順で扱う
   1. メンテナ（または CC）が、提案を決定 3 の条件に照らす。提案の中の事実（「既製品が無い」「この手順で動く」など）は、開発専用の `/verify-issue` で確かめる
   2. 条件ごとの判定（満たす / 満たさない / 確かめられない）を Issue にコメントで返す。満たさない条件があれば、どう変えれば満たすかを書く
   3. 条件を満たし、メンテナが採ると決めたら、ADR を `proposed` で起票し、Issue から ADR へ参照する。accepted になってから実装する
   4. 採らない場合は、理由を書いて Issue を閉じる。事業固有の作業や、使う利用者が限られる作業なら、利用者の company で業務 Skill として育てる方法を案内する
   5. 提案に SKILL.md の案やコードが添えられていても、そのまま取り込まない。設計の参考にし、business-os の規約に沿って書き直す（20260929-08）。
      添えられた内容に事業データや認証情報が含まれていたら、引用せずに提案者に伝える
   - 提案のフォーム（`.github/ISSUE_TEMPLATE/proposal.yml`）に、決定 3 の条件に答える項目（どの分類か、既存の Skill の手順の追加で済まない理由、既製品を探したか、外部のツールに頼るか）を足す
5. 配布した Skill を減らす経路を持つ
   1. 利用者の `/retro` が、使われていない business-os の Skill を「business-os への改善案」として挙げられるようにする（剪定の対象を業務 Skill に限っている今の記述を広げる）
   2. 利用者が Issue で Skill の削除や統合を提案できるようにする。`/retro` の改善案も、Issue として届く（報告の導線は 20261004-01）
   3. Issue で届いた削除の提案は、決定 4 と同じ順で扱う。提案の中の事実（「使われていない」「別の Skill と重なる」など）を確かめ、
      判定を Issue に返し、外すと決めたら ADR を `proposed` で起票する。外さない場合は理由を書いて Issue を閉じる
   4. 外すと決めた Skill は、すぐに消さない。外す版の前に CHANGELOG と `docs/usage/` で予告し、使い続けたい利用者には、
      company の `.claude/skills/` に業務 Skill として写して使う方法を案内する（外した Skill を呼ぶ手順が黙って壊れないようにする）
   - 提案のフォームに、削除の提案を選べる項目（追加 / 削除・統合 / そのほか）を足す
6. 一覧と実物の照合は続ける。`check:skills` と起動時の点検は、分類ごとの名前の一覧と `skills/` のフォルダが一致しなければ、今と同じく fail / warn にする。
   点検のメッセージと文書から「10 個」の数を外し、数を書く代わりに一覧（コード）を正本として指す

## 影響

- 良い影響
  - 条件を満たす Skill（報告の Skill など）を、数の都合で退けずに議論できる
  - 事業に依存しない業務の Skill（共通業務 Skill）の置き場ができる。利用者が company で一から作らずに済む
  - 増やす条件と減らす経路が明文化され、追加の判断が ADR ごとに残る
  - 利用者が Issue で Skill の追加や削除を提案したときの扱いが決まり、提案者は条件ごとの判定と、採らない場合の代わりの方法（company の業務 Skill）を受け取れる
  - 外す Skill を使い続けたい利用者は、予告を見て company に写せる。手順が黙って壊れない
  - 一覧と実物の照合は残るので、欠落や紛れ込みは今と同じく点検で止まる
  - 文書が数を書かなくなり、Skill を足しても文書の数字が古くならない
- 悪い影響
  - 数という分かりやすい歯止めが無くなる。条件の判断が甘いと、Skill が少しずつ増える
  - 配布した Skill の使われ方は各利用者の company にあり、メンテナには直接見えない。減らす判断は、利用者が `/retro` や Issue で知らせてくれるかに頼る
  - Skill を外すときは予告の期間が要り、すぐには減らせない
  - 実装で、一覧の持ち方（分類つき）、点検のメッセージ、文書の 7 か所の記述を直す必要がある
  - 共通業務 Skill は外部のツールとつながるので、経営基盤 Skill より守ることが多い（未接続のときの止まり方、外部への行動の確認、外から読んだ内容の扱い）。
    Skill の動作の検証も、ツールが無い場合のケースを含める必要がある
- その他
  - 実装は別の PR で行う。`FOUNDATION_SKILLS` を分類つきの一覧に改め、`check:skills`・起動時の点検・`/retro`・文書・提案のフォームを合わせる
  - 20260929-07 は全体としては有効なまま残る。この ADR が accepted になったら、20260929-07 に「Skill の数の固定は 20261004-02 で置き換えた」という 1 行を足す（決定の本文は書き換えない）
  - 利用者の Skill の一覧が長くなりすぎたと分かったら、上限（案 D）を改めて検討する
  - 共通業務 Skill の具体的な候補（メールの整理など）は、この ADR では決めない。決定 3 に沿って Skill ごとに ADR で決める

## 案ごとの長所と短所

### 案 A：10 個で固定する

- 長所：歯止めが最も分かりやすい。実装も文書も変えなくてよい
- 短所：条件を満たす Skill も数の都合で退ける。追加したい Skill が出るたびに、既存の Skill への手順の押し込みか、固定の見直しの議論が起きる

### 案 B：経営基盤 Skill は固定のまま、サポート Skill を数の外に設ける

- 長所：経営基盤の歯止めはそのまま残る。報告の Skill はすぐに入れられる
- 短所：サポート Skill の側には数の歯止めも条件も無く、そちらに Skill が流れ込みうる。経営基盤 Skill を増やしたくなったら、固定の見直しの議論をくり返す

### 案 C：数の固定をやめ、分類ごとの追加の条件と ADR で決める

- 長所：20260929-07 の狙い（使われない Skill を増やさない）に、条件と剪定の経路で直接効く。分類が違う Skill（共通業務・サポート）も同じ条件で判断できる
- 短所：数の歯止めが無くなり、条件の運用に頼る。減らす判断の材料が利用者からの報告に限られる

### 案 D：数の上限を設ける

- 長所：歯止めの分かりやすさを保ちつつ、少しは増やせる
- 短所：上限の数に根拠が無い。上限に近づくと案 A と同じ問題が起きる
