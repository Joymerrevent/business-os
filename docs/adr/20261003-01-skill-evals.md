# 20261003-01: Skill の動作は claude plugin eval で CC が手元で検証する

## 背景

`pnpm check` と `pnpm test` は、hook・検査スクリプト・配布物の形を確かめる。
一方で、Skill を実際に動かしたときの振る舞い（`/onboard` が何をどの順で書き出すか、など）は、
メンテナが手順書を見ながら対話モードで 1 項目ずつ手で確かめてきた。
手での確認は 1 回 30〜40 分かかり、Skill・雛形・hook を変えるたびに繰り返すと続かない。
20260929-06 が退けた「点検を人間の習慣に任せる」と同じ形の弱点で、確認が抜けた変更は静かに壊れる。

Claude Code 2.1.269 以降には `claude plugin eval` がある。Plugin だけを読み込んだ使い捨ての環境で `claude -p` を走らせ、
作られたファイル・ツールの呼び出し・最終応答を採点し、成否を終了コードで返す。

### 試作で確かめたこと（2026-10-03、Claude Code 2.1.285、macOS、Sonnet）

`/onboard` の初回の導入を 1 ケース・1 回だけ動かした。

| 項目 | 結果 |
|---|---|
| 所要 | 約 50 秒、36 ターン |
| 消費 | API の定価換算で約 0.24 USD（判定モデル分は約 0.001 USD）。claude.ai のログインで動かすと、請求ではなくサブスクリプションの利用枠を消費する |
| 確かめられた | `.business-os.json` を最初に書く、地図・憲章・台帳・事業ごとのファイルを書き出す、`{{` が残らない、Obsidian を使わない場合に Obsidian のファイルを作らない、答えが文書に反映される |
| 確かめられなかった | `.claude/settings.json` の書き込み。`Write` を許可しても、eval の実行環境（don't ask mode）が拒否した。CC は別の手段で書こうとせず止まった。このため `state: active` への切り替えまで進まない |
| 使えない | AskUserQuestion。`claude -p` では提供されない（別途 `claude -p` 単体でも確認） |
| 環境の制約 | Bash を許可する実行は、開発機の `~/.docker` にシンボリックリンクがあると sandbox が締め出せず、実行自体が始まらない |

入力欄から起動した Skill は Skill ツールの呼び出しとして記録されないため、`tool_used: Skill` では起動を判定できないことも分かった。

## 決定

1. Skill の動作の検証は `claude plugin eval` で行い、CC が手元で実行する。メンテナの手での確認は、eval で確かめられない項目だけに絞る
2. ケースは `evals/<Skill 名>/<ケース名>/` に置く（`prompt.md`、`case.yaml`、`graders/`）。実行結果（`evals/results/`）は `.gitignore` に入れる
3. 対話する Skill は「回答表」で動かす。利用者が答える内容をプロンプトに並べ、`append_system_prompt` で
   「利用者は不在。質問せず回答表を使う」と指示する。1 問ずつ聞く流れそのものは、この方式の検証の対象外とする
4. 判定は無料の方式（`file_exists`、`regex`、`tool_used`、`tool_order`）を主にする。
   `llm` による判定は文書の中身の確認に限って補助として使う。Skill の起動は `tool_used: Skill` ではなく、記録（`trace`）への `regex` で判定する
5. 実行の既定は Sonnet・1 ケース 1 回・`--ablation none`。合否の閾値は既定の 1.0（全項目合格）
6. CI には載せない。`pnpm check`（`check:*`）にも含めない。`package.json` には `check:` で始まらない名前の script として置く
7. Skill・雛形（`templates/`）・hook を変える PR では、CC が該当するケースを実行し、結果の要約を PR の本文に書く

### 後続の検討とするもの（この ADR では決めない）

- `.claude/settings.json` の書き込みと `state: active` への切り替え（`/onboard` の最後の段階）の自動検証
- Bash を許可する実行の環境の整え方（`/check` や git のコミットを含むケース）。Linux の CI で動かすかも含む
- 1 ターンずつ進めて質問の流れを確かめる進行役（`claude -p --resume` を TypeScript で回す）
- 導入済みの company を前提にするケースで、`test/fixtures/company/` を scaffold から使えるか

## 根拠

- 公式の仕組みを使う。採点・費用の上限・終了コード・使い捨ての環境が揃っており、自前で作る量が最も少ない
- 手順書の「期待する結果」の多くは、ファイルの有無・中身の文字列・書き込みの順番で書ける。無料の判定方式でそのまま採点できる
- `llm` 判定は 3 票の多数決で、票が割れることがある（試作でも 1 対 2 に割れた）。判定を主にすると結果が揺れる
- CI に載せない理由：API キーで動かすと別途請求が発生する。手元なら利用枠の範囲で済む。1 回あたりの消費は小さく、PR ごとに手元で回せる
- 検討した代替案
  - 自前の進行役だけで作る → 採点・費用管理・隔離を作り直すことになる。質問の流れの検証が要るときに後から足す（後続の検討）
  - 手での確認を続ける → 続かない。不採用

## 影響

- `evals/` が増える。CLAUDE.md の「何がどこにあるか」に追記する（実装 PR で行う）
- eval の実行環境では、利用者の設定・`CLAUDE.md`・他の Plugin が読み込まれない。business-os の hook は読み込まれるため、hook を含めた振る舞いを確かめられる
- 実行のたびにメンテナの利用枠を消費する。1 ケース 1 回で済ませ、回数を増やすのはリリース前など必要なときに限る
- eval で確かめられない項目（上の後続の検討、Obsidian の画面操作など）は、引き続き手で確かめる。手での確認の手順はその項目だけに絞る
