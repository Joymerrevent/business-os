# 20261002-01: 役割エージェントは business-os に含めない

## 背景

2026 年 5 月版の business-os は、Secretary / CFO / CTO / CMO / CSM / Editor / Adversarial といった
役割ごとのエージェント（サブエージェントの定義）を中核に置いていた。

2026 年 9 月の再設計では、中核を経営基盤の Skill 10 個（20260929-07）に移した。
その際、役割エージェントを含めないという判断を明示していなかった。
判断が書かれていないと、「以前あったものが抜けている」のか「意図して外した」のかが区別できず、
後から役割エージェントを足す変更が、設計の検討なしに入りうる。

## 決定

1. 0.x の business-os に、役割エージェントを含めない（`agents/` を置かない）
2. 役割エージェントが必要になったら、利用者の `company/.claude/agents/` で育てる（業務 Skill と同じく business-os の外）
3. `/retro` が「同じ視点のレビューを 2 回頼んだ」ことを検出し、役割エージェントにすることを提案する（2 回ルール）
4. 育てた役割エージェントのうち、事業非依存と分かったものだけを、ADR を経て business-os に昇格させる

## 根拠

- 最小から始めて、使った分だけ育てる（20260929-07）。役割エージェントも、使われるかどうかは運用してみないと分からない
- 他人の多役割の構成は、大半が冗長になる（20260929-08 の gstack の評価）。35 コマンド中で定着したのは 6 つだった
- 役割の視点は、すでに Skill に埋め込まれている
  - `/close`：財務の視点（事業ごとの収支、資金、数字の基準日）
  - `/validate`：新しい施策の検証ゲート（仮説、撤退条件、上限）
  - `/quarterly`：経営のレビュー（継続 / 縮小 / 撤退）
- 文脈の分離（本セッションの文脈を汚さない分析）は、汎用の Agent ツールで足りている。
  `/quarterly` と `/retro` は分析をサブエージェントに任せ、質問と書き込みを本文脈で行っている（Phase 0 の検証項目 11）
- 検討した代替案：2026 年 5 月版の役割エージェントをそのまま移す → Skill と役割が重複し、
  どちらを呼ぶべきかの判断が利用者に生じる。使われない役割の保守も残る。不採用

## 影響

- business-os のリポジトリに `agents/` を置かない。構造仕様（architecture.md §3）に明記する
- 昇格の経路（`company/.claude/agents/` → `/retro` の提案 → ADR → business-os）を構造仕様（§6）に明記する
- 最初に昇格する候補は「反対役」（読み取り専用で、提案を批評する）と予想する。
  `/approve` の前に提案の弱点を洗い出す用途は、事業に依存しないため
- `/retro` の集計に「同じ視点のレビューの依頼」を加える場合は、`/retro` の SKILL.md の変更として別に行う
