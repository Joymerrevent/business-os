# 20261002-01: 役割エージェントは同梱せず、主セッションを COO とする。作業は作業者へ委譲する

## 背景

2026 年 5 月版の business-os は、Secretary / CFO / CTO / CMO / CSM / Editor / Adversarial といった
役割ごとのエージェント（サブエージェントの定義）を中核に置いていた。

2026 年 9 月の再設計では、中核を経営基盤の Skill 10 個（20260929-07）に移した。
その際、役割エージェントを含めないという判断を明示していなかった。また、「誰が会社の運営を回し、組織を育てるのか」と、
「大きな作業をどこで行うか（主セッションの文脈と利用枠をどう守るか）」も決めていなかった。

## 決定

### 主セッションを COO とする

1. 主セッション（利用者が対話している CC）を、その会社の COO と位置づける。COO は周期の業務を回し、
   判断と人との対話に集中し、仕組みを育てる
2. COO は、人との対話を含まない大きな作業を、作業者エージェントに委譲する

### 委譲の閾値

| COO が自分で行う | 作業者に委譲する |
|---|---|
| 人との対話を含むもの（質問、承認、確認） | 多数のファイルの読み込みと要約 |
| 1〜2 ファイルの小さな読み書き | 調査 |
| 判断そのもの | 下書きの大量の生成 |
| | 並列にできる独立した作業 |

委譲は絶対ルールにしない。小さな作業を委譲すると、作業者の起動と指示の受け渡しという固定費の分だけ割高になるため。

### 役割エージェントと作業者エージェントを区別する

| | 役割（視点）エージェント | 作業者エージェント |
|---|---|---|
| 何か | CFO・CTO・反対役など、特定の視点で判断や批評をする | 視点を持たず、指示された作業をこなす |
| business-os に同梱するか | **同梱しない**（`company/.claude/agents/` で育てる） | **1 体だけ同梱する**（`agents/worker.md`） |

1. 0.x の business-os に、役割エージェントを同梱しない
2. 作業者エージェント `worker` を 1 体だけ同梱する。汎用の作業者で、モデルは `sonnet`、ツールはファイルの読み書きと検索だけ。
   人との対話（できない）と外部への行動はしない。視点を持たないので、上の「役割エージェントは同梱しない」と両立する
3. 役割エージェントが必要になったら、`company/.claude/agents/` で育てる。COO（`/retro`）が「同じ視点のレビューを 2 回頼んだ」を
   検出して提案する（2 回ルール）。事業非依存と分かったものだけを、ADR を経て business-os に昇格させる

### モデル

1. 主セッション（COO）のモデルは `/onboard` で聞く。既定は `best`（使える最上位。Fable が使えれば Fable、無ければ Opus）。
   質問文は「主セッションのモデル。best 推奨（使える最上位）。利用枠を節約するなら opus」。
   利用者が選んだ値を company の `.claude/settings.json` の `model` に書く
2. 作業者 `worker` のモデルは `sonnet`
3. モデルは別名（`fable` / `best` / `opus` / `sonnet` / `haiku`）で書き、版番号を書かない（版が上がっても書き換えずに済む）

## 根拠

- **先行事例の分業**：高性能なモデルが全体を指揮し（Orchestrator）、廉価なモデルが作業をこなす（Implementer）という分業が、
  エージェントの構成で一般的になっている。判断と対話に上位のモデルを使い、量の多い作業を廉価なモデルに任せると、
  利用枠を節約でき、主セッションの文脈も作業の中間結果で汚れない
- **作業者は対話できない**：サブエージェントの中からは質問できない（architecture.md 第 11 節の項目 11）。
  そのため、人との対話を含む仕事（COO の中核）はサブエージェントに任せられず、主セッションが担うしかない。
  逆に、対話を含まない作業は、作業者に任せても失うものが無い
- **役割の視点は Skill に埋まっている**：`/close` は財務の視点、`/validate` は新しい施策の検証ゲート、`/quarterly` は経営のレビュー。
  役割エージェントを同梱すると、Skill と役割が重複し、どちらを呼ぶかの判断が利用者に生じる
- **最小から育てる**（20260929-07）、**他人の多役割の構成は大半が冗長**（20260929-08 の gstack の評価。35 コマンド中で定着したのは 6 つ）
- **`best` を既定にする**：利用者のプランや提供元の違い（Fable が使えるかどうか）を、別名の解決が吸収する
- 検討した代替案
  - 2026 年 5 月版の役割エージェントをそのまま移す → Skill と役割が重複し、使われない役割の保守も残る。不採用
  - COO をサブエージェント（`agents/coo.md`）として同梱する → 人と対話できないので、COO の中核（相談・承認）を担えない。不採用
  - `advisorModel`（主のモデルが節目だけ上位のモデルに相談する公式の機能）を使う → 今回は採用しない。
    主セッションに上位のモデルを使い、作業を下位のモデルに委譲する構成で足りており、相談の仕組みを重ねる必要が今は無い

## 影響

- business-os に `agents/worker.md` を置く。`agents/` には作業者だけを置き、役割エージェントは置かない（architecture.md §3）
- 委譲の閾値を構造仕様に書く（architecture.md §6.2）。分析を委譲する Skill（`/quarterly` `/retro`）は `worker` を使う
- company の地図（`templates/CLAUDE.md.tmpl`）の「自分は何者か」に、COO の役割と委譲の方針を書く
- company の `.claude/settings.json` の雛形に `model` を足し、`/onboard` が利用者の答えを書く
- business-os の hook は、作業者のツール呼び出しにも発火する（公式の仕様）。実機の発火試験（`/check` の `--live`）で、作業者に委譲した書き込みが
  止まることも確かめる
- Fable は安全分類器に引っかかると、自動で別のモデル（Opus）に切り替わることがある。その場合は `/model fable` で戻せる。
  利用者向けの文書に一言書く
- 最初に昇格する役割エージェントの候補は「反対役」（読み取り専用で、提案を批評する）と予想する。
  `/approve` の前に提案の弱点を洗い出す用途は、事業に依存しないため
