# 20261003-08: Skill が人に聞く質問は、SKILL.md の質問の表で番号・見出し・質問文を固定する

## 背景と問い

business-os の Skill は、SKILL.md の「人に何を聞くか」の節に、聞く項目を箇条書きで並べている。
質問の言い回し・まとめ方・順番の細部は、実行のたびに CC が決める。例外は `/onboard` の主セッションのモデルの質問で、質問文を SKILL.md に固定している。

2026-10-03 に、質問の流れを確かめる進行役（20261003-02）で `/onboard`・`/validate`・`/adr` の台本を実行し、次のことが分かった。

- 同じ Skill の同じ質問でも、実行ごとに形が変わる。`/onboard` の 1 問目は、「会社の呼び名を教えてください」と 1 文で聞く回と、「会社について教えてください」の下に 4 項目を箇条書きにする回があった
- 事業 ID の確認は、単独のターンで聞く回、次の質問と同じターンで「変えたい場合はお知らせください」と添えるだけの回があった
- 進行役は質問をキーワードで見分けるため、言い回しの揺れで 9 回誤判定した（前置きの「git リポジトリ」、ID の説明の「英小文字・数字」、補足の「外部に影響が出る行動」、予告の「背景は、このあと聞きます」など）。その都度キーワードと判定を直した

揺れは利用者にとっても同じ問題である。同じ Skill を毎週・毎月使うのに、聞かれ方が毎回違うと、答え方を毎回読み直すことになる。

問い：Skill が人に聞く質問を、毎回同じ形にするか。するなら、どこに何を固定するか。

## 判断の基準

- 利用者が、同じ Skill で毎回同じ質問を同じ順で受けること
- 進行役が、言い回しに左右されずに質問を見分けられること
- CC が状況に合わせて考える部分（数字やリスクの候補、読んだ文書の要約、聞き返し）を失わないこと
- Skill の起動のたびに確実に読まれること（読み忘れの余地が無いこと）
- 新しく足す Skill も同じ形に従い、それを機械で検査できること

## 検討した案

- 案 A：各 SKILL.md の「人に何を聞くか」の節を質問の表にし、番号・見出し・質問文・答えの形を固定する
- 案 B：質問を Skill ごとの別のファイル（例：`skills/<名前>/questions.md`）に置き、SKILL.md から指す
- 案 C：質問は固定せず、進行役のキーワードと判定を直し続ける（今のまま）

## 決定

採用：**案 A**。SKILL.md は Skill の起動時に必ず読まれ、別のファイルを読みに行く手間と読み忘れが無い。番号と見出しで見分ければ、進行役は言い回しに左右されない。

1. 各 SKILL.md の「人に何を聞くか」の節を、次の列を持つ質問の表にする

   | 列 | 中身 |
   |---|---|
   | 番号 | 1 から始まる連番 |
   | 見出し | 質問を短く表す名前。12 文字以内（AskUserQuestion の `header` の上限） |
   | 質問文 | 利用者に見せる文。そのまま使う |
   | 答えの形 | 自由記述、選択肢（単一）、選択肢（複数）のどれか |
   | 選択肢 | 選択肢の質問だけ。並びと推奨（あれば）も固定する |

2. CC は、質問するときに「質問 <番号>/<総数>：<見出し>」を付け、質問文をそのまま使う
   - 質問の前に、読んだ文書の要約や CC が考えた候補を添えてよい
   - 1 つのターンで 2 つ以上の質問をしない
   - 聞き返すときは「（質問 <番号> の確認）」を付ける
   - 事業ごとなど同じ質問をくり返すときは、同じ番号と見出しに対象を添える（例：「質問 6/9：追いかける数字（事業 A）」）
   - 答えの形が選択肢の質問は、AskUserQuestion の `header` に見出し、選択肢に表の選択肢をそのまま使う。AskUserQuestion が使えない環境では、同じ選択肢を文章で示す
3. 条件によって聞かない質問（例：`/approve` の「却下の理由」は却下したときだけ）は、表の行に条件を書く。聞かないときは番号を飛ばしてよい
4. 確認（「書き出してよいか」「コミットしてよいか」）も質問の表に入れる。Claude Code や hook が出す権限の確認は、Skill の質問ではないので表に入れない
5. `pnpm check`（`check:skills`）で、各 SKILL.md に質問の表があること、番号が 1 からの連番であること、見出しが 12 文字以内であることを検査する
6. 質問の流れの進行役は、台本の項目を見出しのキーワードではなく、質問の番号で見分ける。台本の各項目には番号を書く

## 影響

- 良い影響
  - 利用者は、同じ Skill で毎回同じ番号・見出し・質問文を受け、あと何問あるかも分かる
  - 進行役の判定が番号の一致だけになり、言い回しの揺れによる誤判定が無くなる。台本のキーワードの調整が要らなくなる
  - 新しく足す Skill も、検査によって同じ形に従う
- 悪い影響
  - 配布する 10 個の SKILL.md を全て書き換える。利用者に届く変更なので changeset が要る
  - 質問文を変えるたびに、SKILL.md・台本・eval の回答表をそろえて直す手間が増える
  - 質問の表が長い Skill（`/onboard` など）は、SKILL.md が長くなる
- その他
  - 実装 PR では、全ての eval のケースと台本を流し直し、結果が変わらないことを確かめる
  - 固定するのは質問の番号・見出し・質問文・答えの形・選択肢だけで、CC が候補を考える部分は固定しない。固定の範囲を広げたくなったら、この ADR を見直す

## 案ごとの長所と短所

### 案 A：SKILL.md の質問の表で固定する

- 長所：Skill の起動時に必ず読まれる。質問と手順が同じファイルにあり、手順の変更と質問の変更がずれにくい。検査しやすい
- 短所：SKILL.md が長くなる。10 個を全て書き換える

### 案 B：質問を別のファイルに置く

- 長所：SKILL.md が短いまま。質問だけを一覧で読める
- 短所：CC が別のファイルを読みに行く必要があり、読み忘れると固定が効かない（20260929-06 が退けた「静かに効かなくなる」形の故障）。手順と質問が 2 か所に分かれ、ずれやすい

### 案 C：固定せず、進行役を直し続ける

- 長所：SKILL.md を変えない。CC が状況に合わせて聞き方を変えられる
- 短所：利用者の体験が揺れたまま残る。進行役のキーワードと判定の調整が終わらない（2026-10-03 の 1 日で 9 回）
