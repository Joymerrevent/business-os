# 20260929-06: 起動時セルフチェック

## 背景

安全装置は、壊れても何も言わない。

- JOINCLASS の AI-CEO Framework では、Skill をフラットな `.md` で出荷していたため、
  CC が `skills/<name>/SKILL.md` として認識せず、setup を実行した全利用者の Skill が
  一切読み込まれていなかった。エラーは出ず、スラッシュコマンドが無いだけ。
  CLAUDE.md が「新施策の前に必須」としていた検証ゲートも含まれ、半年近く静かに何もしていなかった
  （2026-09-25 の修正 PR で判明）
- gstack では 4 つのセキュリティガードが fail-open（壊れて全部通す）になっていた

使っている本人は「ゲートがある」と思い込む。これが最も危険な故障。

## 決定

### 軽い点検（毎セッション）

器の `hooks/session-start.ts` が SessionStart で毎回走る。目標 1 秒未満。読むだけで何も書かない。
**全部 OK なら無言、問題があるときだけ表示**。
`.business-os.json` が無いディレクトリ（company ではない）では何もしない。

| # | 確認 |
|---|---|
| 1 | Node が器の要求バージョン（24 系）か |
| 2 | 器の 10 Skill が全て存在し、フロントマターに `name` `description` があるか |
| 3 | `hooks.json` が指すスクリプトが全て存在するか |
| 4 | `company/.claude/settings.json` に期待する sandbox / permissions 規則があるか |
| 5 | `.business-os.json` の `state` が `active` か（`initializing` のままなら `/onboard` の再開を促す） |
| 6 | `proposals/` に `approving` のまま 24 時間以上経過したものがないか |
| 7 | `company` が記録する器のバージョンと Plugin の実バージョンが一致するか |
| 8 | hook のログファイルに書き込めるか |
| 9 | sandbox が使える環境か（native Windows 等では warn。厳格モードにはしない） |
| 10 | 器の Skill と同名の Skill が利用者側（`company/.claude/skills/`、`~/.claude/skills/`）に無いか（あれば warn。同名なら利用者側が優先されるため） |

**厳格モード**：`state: active` で 4 が異常なら、hook は保護対象への Write / Edit を提案の有無に関わらず全拒否し、
「防衛設定を復旧せよ」と返す。第一・二層が欠けた状態で第三層だけに頼らない。

### 重い点検（週次、`/check`）

器の `scripts/check.ts` を `company` に対して実行し、`docs/operations/reviews/check-YYYYMMDD.md` に書く。
判定は pass / warn / fail、全体の成否は **終了コード**で判定する（Done の数を数えない）。

| 分類 | 確認 |
|---|---|
| 防衛の発火 | hook に合成入力を渡し、`charter/` への Write が exit 2、フロントマター欠落が exit 2、正常が exit 0、内部例外注入が exit 2 になるか |
| 防衛の発火 | Bash で `charter/.probe` への書き込みを試み、ファイルが作られないか |
| 設定の一致 | `settings.json` が雛形の必須規則を含むか、`claude plugin validate` が通るか |
| 文書の規約 | `docs/**` のフロントマター：4 日付欄、`YYYY-MM-DD` or `n/a`、`updated ≥ created`、ID 形式 |
| 鮮度 | `charter/*` の `verified` 90 日超、`operations/state/*` の `updated` 14 日超、`decisions/` の `proposed` 30 日超、`approving` 24 時間超（いずれも warn） |
| リンク | `docs/**` の相対リンク切れ |
| 漏洩 | gitleaks、`.env*` の追跡有無 |
| Git | 未コミット変更の放置、未 push、現在ブランチ（warn） |
| 指示ファイル | `CLAUDE.md` 70 行超で warn、`/doctor prompt-audit` の結果要約（範囲を company の指示ファイルに限定して呼ぶ。未指定だと `~/.claude` まで読むため） |
| Obsidian（使用時） | `.obsidian/workspace*.json` の gitignore、`.base` の破損 |
| 利用統計 | 過去 7 日の Skill 実行回数（`/retro` の材料。判定なし） |

### 共有

判定コードは器の `pnpm check`（`check:*`）と同じライブラリを使う。器側は Skill 規約や配布物の検査、
`company` 側は防衛と文書の検査、と対象が違うだけ。

## 根拠

- 「設定がある」ではなく「効いている」を確認する。合成入力を hook に渡す、sandbox に実際に書き込みを試みる。
  この種のテストがあれば JOINCLASS も gstack も初日に見つかっていた
- porters-connect の規約「成否は終了コードで見る。Done の数で数えない」（数えて見逃し、CI で落ちた実例）を採用
- 軽い点検を毎回走らせるのは、静かな故障を最大 1 セッション以内に検出するため。重い点検を週次に分けるのは、
  毎回やると起動が遅くなるため
- 検討した代替案：点検を人間の習慣に任せる → 続かない。不採用

## 影響

- 器のバージョンと `company` の記録を照合するため、`/onboard` は器のバージョンを `company` に書き残す
- 厳格モードは運用中（`state: active`）の `company` でだけ発動する。`/onboard` 前（対象外）と初期化中は発動しない
- `/check` のレポートは `operations/reviews/` に溜まる。Obsidian の Bases で一覧できる
